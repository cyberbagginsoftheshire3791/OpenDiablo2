# M4.6 world save: carry-overs from B1's review

Short, and owned. Each entry below is something burst B1 (the counted streams
and the observed fields, branch `save-b1`) found and did NOT build, with the
later burst that owns it. Written 27 Sep 2026 after an independent review of
B1; the build plan itself is the main session's.

## 1. "Load last save" is not a seeded game (owner: B4b)

Only `strigoi_start_game` seeds a game. It sets the server's one-shot seed
(`d2server.SetNextGameSeed`) and reseeds the harness's uuid stream
(`d2app/harness_uuid.go`), then begins the game. The death screen's "load last
save" goes `App.ReloadGame` -> main menu -> `ToCreateGame` (`d2app/reload.go`)
and does neither, so the reloaded game, in a process that was seeded:

- takes a **wall-clock server seed**: `takeNextGameSeed` is one-shot and the
  first game consumed the override. The world RNG, the spawn tables, combat and
  the rising all seed from `gameClient.Seed`, so all four start where no script
  chose;
- **continues the uuid stream** from the dead game's byte count: its player id
  (the connection's uuid) and every entity id are the seed's later ids;
- therefore matches **no fresh launch**. It is deterministic only for the same
  script in the same process.

How to see it: the `uuid` provider reports `seeded_for_this_game` (false on a
reloaded game), `games` (= `seeded_game + 1` there) and `bytes_at_game_start`
(the dead game's count); every stream's `rng.seed_str` shows the wall-clock
seed. Pinned as it is today by `d2app` `TestUUIDStreamOnAFreshLaunchAndOnAReload`
(both halves) and `TestTownWalkDeterministic` (the fresh half).

**B4b** restores these on a load: the server seed from the save, and the uuid
stream with `d2rand.RestoreReader(seed, bytes)` AFTER the entities are rebuilt
(the plan's trap 6). When it does, the reload half of the unit test changes
with it, on purpose.

## 2. Seeds are int64; decode them as int64 (owner: B2, the world file)

A wall-clock seed (UnixNano, ~1.8e18) is past 2^53, where float64 stops
holding every integer. A reader that decodes JSON into float64 -- every
playtest's `mustNum` does -- reads a DIFFERENT seed, and a stream restored from
it is a different stream from its first value. So every stream report carries
`seed_str` (exact decimal) beside `seed`, and **the world file must decode
seeds as int64** (`json.Decoder.UseNumber` then `Int64`, or a typed struct
field), never through `interface{}`/float64. `d2rand`
`TestSeedStrSurvivesAFloat64Decoder` shows the loss and both exact routes.

## 3. A stream is one value (done in B1; for B2's Restore)

Spawns, Combat and Rising each hold one `*d2rand.Stream` (the `*rand.Rand` and
its counted source), and `Stream.Restore(seed, draws)` replaces both at once.
B2's system Restore calls that and nothing else. Do not take `.Rand` out of a
stream and keep it: after a Restore it draws from the old, uncounted source.
The map engine is the exception, because its stream is handed to two factories:
`MapEngine.RestoreRand` goes through `useRand`, which re-hands it, and
`TestRestoreRandHandsTheStreamToTheFactories` holds it there.

## 4. A pack's members include its dead (for B2's snapshot)

`group.members` is never shortened: a death unwatches its member (combat's
`withdraw`) and the group keeps him, and the game reads the dead there --
`spent()` is "no member still watched" over the whole list, a dead man's
profile still names his pack, and a despawn takes every member off the map. `spawns.group_list[].member_ids` reports every
member as placed, dead ones included; the `notice` rows are only the watched.
The snapshot must carry `member_ids`, not the notice rows.

# B2b: the snapshots that carry entity ids (branch `save-b2b`, 28 Sep 2026)

Three world systems that point at entities -- Spawns, Notice and Pursuit --
gained `Snapshot(r)` and `Restore(snap, r)` through a `Resolver`. The game
spawner gained its own small pair, the entity factory gained the next-id seam,
and creatures and NPCs gained a motion snapshot. Nothing in the game calls
any of it yet: B3 writes the snapshots, B4b restores them.

The work was started on 27 Sep and cut off before review or gate. It was then
inherited, audited field by field against build plan section 5, fixed, and
closed on 28 Sep. "What the audit changed" below lists what the first draft
got wrong.

## The Resolver (`d2core/d2world/resolver.go`)

```go
type Resolver interface {
	Watcher(id string) (Watcher, bool) // the live entity with this id
	Quarry(ref string) (Quarry, bool)  // PlayerRef is the player; else an entity id
}
const PlayerRef = "player"
```

- **No remap table.** Every entity comes back with its saved id (the seam
  below), so a Resolver is a lookup, not a translation. The player is the one
  exception: his id is his connection's uuid and is new every launch. So every
  record that points at him is written as the word `player`.
- **Strict at load.** An id that does not resolve is `ErrUnresolvedRef`, never
  a silent drop. So is an id that resolves to something answering to another
  id. A chase's hunter must also be a `Hunter`, which is the type assertion
  `startChasesForTheAware` makes on the live path.
- **Strict at save.** `Snapshot(r)` takes a Resolver over the LIVE world:
  - it names the player through it. If there is a watch or a chase and no
    player, the snapshot is refused;
  - every ref it writes must resolve now, so a file no load could read is
    refused before it is written.
- **All-or-nothing.** Every Restore checks the whole snapshot before it
  changes anything, so a refused one leaves the system exactly as it was.
- The shared helpers sit beside the interface (`b2bResolveWatcher`,
  `b2bResolveQuarry`, `b2bLivePlayerID`, `b2bSavedRefsResolve`,
  `b2bCheckNumbers`). All are B2b-private. There is no shared `snapshot.go`.
- **The game's Resolver is B4b's to write.** It must be built over
  `MapEngine.Entities()`, and it must return the same adapter the live path
  builds: a `chaser` wrapping the entity, with `Quarry(PlayerRef)` giving
  `prey{localPlayer}`. The save and the load must use the same Resolver type.

## Spawns (`SpawnsSnapshot`, `spawns_snapshot.go`)

| Field | Treatment |
|---|---|
| every group: `id`, `row`, `code`, `members`, `morale`, `born_at`, `band`, `stage` (by name), `weight`, `spawned`, `born_where` | **S** |
| `next_id`, `since_check_minutes`, `open_bodies` | **S** |
| the eight counters: `checks`, `rolls`, `spawned`, `failures`, `dropped`, `despawned`, `cleared`, `released` | **S** |
| `rng {seed, draws}`: the tables' `d2rand.Stream` | **S**. The seed is a JSON string, exact past 2^53. It has the same shape as B2a's Combat and Rising streams |
| `sheltered` | **T**. Snapshot is refused while it is set, because a sleep is running |
| the dials | **D** |
| clock, notice, illumination, spawner, target, chases, the `layDead` hook | wiring |

**Members** are saved as `{id, x, y, gone}`, and the dead are included (B1's
`member_ids`).

- **A member on the map** must resolve at load, to an entity standing EXACTLY
  at the saved x,y. The position is an identity check, not a second copy of
  his motion. The wrong entity is refused, and so is one whose motion was not
  restored first.
- **A gone member** was in his group and not on the map at save: a slain man
  whose body stood up, so `takeOffTheMap` took his remains.
  - Gone is decided at save by the live Resolver, then **checked against the
    notice model**. A death unwatches a man (`Combat.withdraw`) before
    anything takes him off the map. So a member the Resolver cannot find
    while notice still watches him is a living wolf the Resolver lost, not a
    dead man, and the save is refused.
  - At load a gone member must NOT resolve. He comes back as a stand-in
    (`b2bGoneMember`) that answers with his id and his last place, which is
    all the game ever asks of him.
  - His x,y is carried and nothing reads it. The sweep pins that as
    `carried`, so it goes red the day something reads it.
- **Refused at load:**
  - a group id that is not `g:<n>` below `next_id`;
  - a row this build's tables do not have;
  - a band outside -1..2, or an unknown stage name;
  - a non-finite number, or a negative count;
  - an id saved twice;
  - a group with no members.

## gameSpawner (`SpawnerSnapshot{arrival}`, `d2game/d2gamescreen/game.go`)

- **S** `arrival`. It sets the next pack's bearing and range (`packSpots`).
  Lost, the next pack comes from the night's first bearing. The scene provider

## The next-id seam (`d2mapentity/entity_id.go`, `d2mapengine/entity_id.go`)

- **`MapEngine.SetNextEntityID(id)` is the one a load calls.** It refuses an
  id already on the map, because `AddEntity` keys on the id and would
  silently replace the first entity. Then it passes the id to the factory's.
- **`MapEntityFactory.SetNextEntityID(id)`** refuses, with `ErrEntityID` and
  not a panic:
  - `""` and `"player"`;
  - an id while another is still waiting;
  - an id the seam has already used.
- **Every constructor that makes a map entity consumes the waiting id, as its
  first statement** (plan: "every constructor that calls newMapEntity").
  - `NewNPC` and `NewCreature` WEAR it. They are the kinds a save rebuilds.
  - `NewPlayer`, `NewMissile`, `NewItem` and `NewCastOverlay` SPEND it
    without wearing it. The player's id is his connection's, and the other
    three are not saved. Wearing it would be worse than losing it: the engine
    map and the notice model would then hold a monster's saved name on a
    missile.
  - `NewObject` does not call `newMapEntity` and is never saved, so it takes
    no part.
  - The id is consumed even when the construction then fails. A consumed id
    counts as used, worn or not.
  - `TestEveryEntityConstructorTakesTheWaitingID` reads the factory's source.
    Every `MapEntityFactory` method that calls `newMapEntity`,
    `newMapEntityWithID`, `NewAnimatedEntity` or `newCreature` must take the
    id in its first statement, so a constructor added later cannot slip past
    the seam. Its positive control is the six names.
- A set id draws nothing from the uuid stream. The load restores the stream's
  count after the entities (trap 6).
- `PendingEntityID()` reports what is still waiting.

## Motion (`d2mapentity/motion.go`): `Creature`/`NPC` `.MotionSnapshot()` and `.RestoreMotion(Motion)`

- **Carried:**
  - `pos`, `target`, `velocity`, `path` and `speed`, in raw sub-tiles, so the
    round trip is bit-exact;
  - `dir` (facing), `mode` (the animation mode), `action` (a held mode) and
    `corpse`.
- **Not carried:**
  - the arrival callback: every monster's walk is handed over with none
    (`chaser.Follow` passes nil);
  - the animation frame: a held action restarts from its first frame;
  - `drawLayer` and `highlight`, which are render state;
  - an NPC's patrol and its per-NPC RNG: only villagers patrol, and the RNG
    has no effect (plan section 1);
  - the directioner, which is wiring.
- **Velocity** is recomputed by the first step. It is seen only at the load,
  by the renderer's debug overlay, and a test pins that.
- **RestoreMotion** sets the fields directly, never through `setTarget`, which
  would re-derive an NPC's mode. A Motion no entity could have had is refused
  before anything changes.
- **Rule 4 ("a walk you were in the middle of does not continue") is the
  player's alone, and it is a B4 load decision.** There is no MotionSnapshot on
  `*Player`, and B2b implements nothing for it. B4 does not restore his walk:
  he stands at his saved x,y. Monsters, the risen and deployed squads keep
  their motion.

## What B4b must do on load, in this order

1. **Rebuild each saved entity:**
   - `engine.SetNextEntityID(id)`;
   - build the saved kind (`NewCreature` or `NewNPC`);
   - **check `entity.ID() == id`.** A mismatch means something else was built
     in between and spent the id; refuse the file (rule 7);
   - `RestoreMotion`, then `AddEntity`.
2. **Assert `PendingEntityID()` is empty.**
3. **Restore through ONE Resolver** built over the resumed map, in this order:
   - `Spawns.Restore`, which also puts the tables' stream back. Nothing in
     between draws from that stream;
   - `Notice.Restore`;
   - `Pursuit.Restore`;
   - `gameSpawner.Restore`.

   Motion must come before Spawns, because Spawns checks positions.
4. **Restore the uuid stream's count after the entities** (trap 6).
5. **Re-apply any harness-set dials.** Dials are never saved, so a script that
   raised `chance` or `max_groups` before saving resumes on the defaults.
6. **Do not restore the player's walk** (rule 4).
7. **Re-id the villagers.** The seam covers only the entities the load builds.
   Villagers already exist when the load runs, so re-iding one needs a verb
   that changes an entity's id and re-keys the engine's map. That verb does
   not exist yet.

## What the audit changed (the first draft's gaps)

1. **The seam covered only NewNPC and NewCreature.** A waiting id could sit
   through any number of other constructions and be taken by whatever monster
   came next. Now every constructor that makes a map entity consumes it, and
   the source test holds that.
2. **"Gone" was the Resolver's word alone.** A Resolver that lost a living
   member would have saved him as dead. At load he would have come back a
   stand-in while his entity walked beside the pack, and a daybreak despawn
   would have left that entity on the map. It is now cross-checked against
   the notice model, and refused.
3. **The spawns stream was written flat** (`rng_seed`, `rng_draws`) while B2a
   writes `rng {seed, draws}`. It now has B2a's shape, so the world file
   carries every stream one way.
4. **The register rows were in a file of their own**, appended at init. The
   register lives in one place (`RegisterMarkdown`'s own comment), so they
   were folded into `register.go`.
5. **An NPC's corpse and held action had no test at all.** The pose half is
   now tested; the composite half needs MPQs (below).

## Found, and left for later

- **The NPC composite pose is not unit-tested.** A composite needs the MPQs.
  Deployed squad models are NPCs (`squadDeployer`), so B4b's playtest must
  cover them.
- **A held action restarts from its first frame.** Saves are refused during a
  fight, so only a swing's tail after a fight can be cut short.
- **Two private stream types with one JSON shape** (`b2aStream`,
  `b2bStream`). Fold them into one in `d2rand` when B2a and B2b are both on
  master.
- **B2a added no register rows for its Snapshot and Restore verbs; B2b
  added defer rows.** The two should agree before B3.
