# M4.6 world save: carry-overs from B1's review

Short, and owned. Each entry below is something burst B1 (the counted streams
and the observed fields, branch `save-b1`) found and did NOT build, with the
later burst that owns it. Written 27 Sep 2026 after an independent review of
B1; the build plan itself is the main session's.

## 1. "Load last save" is not a seeded game (owner: B4b)

Only `strigoi_start_game` seeds a game. It sets the server's one-shot seed
(`d2server.SetNextGameSeed`) and reseeds the harness's uuid stream
(`d2app/harness_uuid.go`), then begins the game. The death screen's "load last
save" goes `App.ReloadGame` -> main menu -> `ToCreateGame` (`d2app/reload.go`)
and does neither, so the reloaded game, in a process that was seeded:

- takes a **wall-clock server seed**: `takeNextGameSeed` is one-shot and the
  first game consumed the override. The world RNG, the spawn tables, combat and
  the rising all seed from `gameClient.Seed`, so all four start where no script
  chose;
- **continues the uuid stream** from the dead game's byte count: its player id
  (the connection's uuid) and every entity id are the seed's later ids;
- therefore matches **no fresh launch**. It is deterministic only for the same
  script in the same process.

How to see it: the `uuid` provider reports `seeded_for_this_game` (false on a
reloaded game), `games` (= `seeded_game + 1` there) and `bytes_at_game_start`
(the dead game's count); every stream's `rng.seed_str` shows the wall-clock
seed. Pinned as it is today by `d2app` `TestUUIDStreamOnAFreshLaunchAndOnAReload`
(both halves) and `TestTownWalkDeterministic` (the fresh half).

**B4b** restores these on a load: the server seed from the save, and the uuid
stream with `d2rand.RestoreReader(seed, bytes)` AFTER the entities are rebuilt
(the plan's trap 6). When it does, the reload half of the unit test changes
with it, on purpose.

## 2. Seeds are int64; decode them as int64 (owner: B2, the world file)

A wall-clock seed (UnixNano, ~1.8e18) is past 2^53, where float64 stops
holding every integer. A reader that decodes JSON into float64 -- every
playtest's `mustNum` does -- reads a DIFFERENT seed, and a stream restored from
it is a different stream from its first value. So every stream report carries
`seed_str` (exact decimal) beside `seed`, and **the world file must decode
seeds as int64** (`json.Decoder.UseNumber` then `Int64`, or a typed struct
field), never through `interface{}`/float64. `d2rand`
`TestSeedStrSurvivesAFloat64Decoder` shows the loss and both exact routes.

## 3. A stream is one value (done in B1; for B2's Restore)

Spawns, Combat and Rising each hold one `*d2rand.Stream` (the `*rand.Rand` and
its counted source), and `Stream.Restore(seed, draws)` replaces both at once.
B2's system Restore calls that and nothing else (through
`d2rand.StreamState.RestoreInto` since the B2 review, after
`StreamState.Check` has refused a stream on another stream's seed or past
`MaxDraws`). Do not take `.Rand` out of a
stream and keep it: after a Restore it draws from the old, uncounted source.
The map engine is the exception, because its stream is handed to two factories:
`MapEngine.RestoreRand` goes through `useRand`, which re-hands it, and
`TestRestoreRandHandsTheStreamToTheFactories` holds it there.

## 4. A pack's members include its dead (for B2's snapshot)

`group.members` is never shortened: a death unwatches its member (combat's
`withdraw`) and the group keeps him, and the game reads the dead there --
`spent()` is "no member still watched" over the whole list, a dead man's
profile still names his pack, and a despawn takes every member off the map. `spawns.group_list[].member_ids` reports every
member as placed, dead ones included; the `notice` rows are only the watched.
The snapshot must carry `member_ids`, not the notice rows.

# B2a: the snapshots with no entity ids (branch `save-b2a`, 27 Sep 2026)

Six systems gained `Snapshot()` and `Restore()`, each in
`d2core/d2world/<system>_snapshot.go` with JSON tags, and each closed by its
`_snapshot_test.go` five ways (the shared helpers are in
`d2core/d2world/b2a_sweep_test.go`, all named `b2a*`):

1. **Round trip.** Snapshot, through JSON, into a FRESH system: the provider
   and the behaviour cannot tell the copy from the original.
2. **Run on.** Both advanced by the same steps stay equal (the provider, and
   whatever else the game reads: levels, bars, blows, bodies).
3. **The sweep.** Every leaf of the snapshot zeroed (or, if already zero, set),
   every list element and object key dropped, one at a time, restored and run
   on: each variant must be REFUSED by Restore or DIVERGE from the original.
   One that does neither fails the test ("losing it changed nothing
   observable"). The only exemptions are named with their reason, must stay
   silent, and must be reached. The first read is taken before the first step:
   what a load shows on its first frame is the save's to get right. **The
   sweep restores the untouched snapshot first**, the same way as every
   variant, and fails unless that matches the original: otherwise a sweep
   whose restore path differs from the original's (a binding in another
   order, a step missed) sees every variant diverge and passes having proved
   nothing (added 28 Sep; see "The finish" below).
4. **Classification.** Every field of every runtime struct a snapshot covers
   is listed as S (saved, with the JSON path it is saved at), D (derived on
   load), T (transient: empty whenever a save is allowed) or W (wiring). A
   field added later fails the test until someone classifies it.
5. **The probes** (`b2aMustDiverge`, added 28 Sep). The sweep counts a refused
   variant as its field seen, but for a field Restore CHECKS -- an id, a next
   id, a count tied to another count -- a refusal proves the check, not that
   the field matters: lost consistently, nothing would refuse. So each such
   field gets a valid-but-wrong value (a fresh model's ids and counts, a next
   id one past the last, another stage, another squad selected, a body
   renamed), which Restore must ACCEPT and the run on must DIVERGE from.

Every Restore is checked whole before it changes anything, so a refused
snapshot leaves the system as it was.

**The streams.** Rising and Combat save their stream as `{seed, draws}` and

## C6: one seed per stream (done in B2a)

`d2rand.Derive(seed, name)` gives the spawn tables, combat and the rising
each its own seed; the world stream keeps the game seed, so the map and the
digest's world part do not move. It works in math/rand's residue space
(`rngSource.Seed` reduces every seed modulo 2^31-1, and two seeds with one
residue are ONE stream), moving the game's effective seed by a fixed
per-name offset (FNV-1a) around the ring of non-zero residues. So for any game
seed the four streams are four different streams -- guaranteed, not merely
likely -- and every derived seed is below 2^31. At seed 1462: spawns
443254809, combat 179919329, rising 1368529044 (pinned by `TestDeriveIsFixed`).

This changes every seeded fight and night once (the rising already had its own
stream, at seed+4707, and now has a derived one). Three scripts were keyed to
an outcome of the old dice; each was re-measured, and each fix also passes on
the old seeding:

- **TestSpawns act 6c** checked the streams' seeds against the old seeding. It
  now checks each against `Derive`, exactly and as `seed_str`, and that all
  four differ. Seen red with combat put back on the game seed.
- **TestCombatResolver act 4** needs the dog dead ("the corpse has no bar").
  Acts 2 and 3 used to kill it on the old dice; on the new ones it stands with
  12 of 61. The script now finishes it with forced crits and fails if eight do
  not -- a corpse is the act's premise, not its finding.
- **TestTacticalFight act 3's control** clicked while his riposte swing was in
  flight (on the new dice the zombie grazes him and he ripostes), and a click
  during a swing is swallowed by the `IsCasting` gate with no notice. The
  control now waits the swing out, as a person would.

**The unaided man's numbers moved** (history 122's winnability measurements
were taken on the old streams). `TestTheUnaidedChain` at seed 1462: old
seeding, he dies at 21:59 with two aware at the peak; new seeding, at 22:29
with one. One encounter either way.

# B2b: the snapshots that carry entity ids (branch `save-b2b`, 28 Sep 2026)

Three world systems that point at entities -- Spawns, Notice and Pursuit --
gained `Snapshot(r)` and `Restore(snap, r)` through a `Resolver`. The game
spawner gained its own small pair, the entity factory gained the next-id seam,
and creatures and NPCs gained a motion snapshot. Nothing in the game calls
any of it yet: B3 writes the snapshots, B4b restores them.

The work was started on 27 Sep and cut off before review or gate. It was then
inherited, audited field by field against build plan section 5, fixed, and
closed on 28 Sep. "What the audit changed" below lists what the first draft
got wrong.

## The Resolver (`d2core/d2world/resolver.go`)

```go
type Resolver interface {
	Watcher(id string) (Watcher, bool) // the live entity with this id
	Quarry(ref string) (Quarry, bool)  // PlayerRef is the player; else an entity id
}
const PlayerRef = "player"
```

- **No remap table.** Every entity comes back with its saved id (the seam
  below), so a Resolver is a lookup, not a translation. The player is the one
  exception: his id is his connection's uuid and is new every launch. So every
  record that points at him is written as the word `player`.
- **Strict at load.** An id that does not resolve is `ErrUnresolvedRef`, never
  a silent drop. So is an id that resolves to something answering to another
  id. A chase's hunter must also be a `Hunter`, which is the type assertion
  `startChasesForTheAware` makes on the live path.
- **Strict at save.** `Snapshot(r)` takes a Resolver over the LIVE world:
  - it names the player through it. If there is a watch or a chase and no
    player, the snapshot is refused;
  - every ref it writes must resolve now, so a file no load could read is
    refused before it is written.
- **All-or-nothing.** Every Restore checks the whole snapshot before it
  changes anything, so a refused one leaves the system exactly as it was.
- The shared helpers sit beside the interface (`b2bResolveWatcher`,
  `b2bResolveQuarry`, `b2bLivePlayerID`, `b2bSavedRefsResolve`,
  `b2bCheckNumbers`). All are B2b-private. There is no shared `snapshot.go`.
- **The game's Resolver is B4b's to write.** It must be built over
  `MapEngine.Entities()`, and it must return the same adapter the live path
  builds: a `chaser` wrapping the entity, with `Quarry(PlayerRef)` giving
  `prey{localPlayer}`. The save and the load must use the same Resolver type.

**Members** are saved as `{id, x, y, gone}`, and the dead are included (B1's
`member_ids`).

- **A member on the map** must resolve at load, to an entity standing EXACTLY
  at the saved x,y. The position is an identity check, not a second copy of
  his motion. The wrong entity is refused, and so is one whose motion was not
  restored first.
- **A gone member** was in his group and not on the map at save: a slain man
  whose body stood up, so `takeOffTheMap` took his remains.
  - Gone is decided at save by the live Resolver, then **checked against the
    notice model**. A death unwatches a man (`Combat.withdraw`) before
    anything takes him off the map. So a member the Resolver cannot find
    while notice still watches him is a living wolf the Resolver lost, not a
    dead man, and the save is refused.
  - At load a gone member must NOT resolve. He comes back as a stand-in
    (`b2bGoneMember`) that answers with his id and his last place, which is
    all the game ever asks of him.
  - His x,y is carried and nothing reads it. The sweep pins that as
    `carried`, so it goes red the day something reads it.
- **Refused at load:**
  - a group id that is not `g:<n>` below `next_id`;
  - a row this build's tables do not have;
  - a band outside -1..2, or an unknown stage name;
  - a non-finite number, or a negative count;
  - an id saved twice;
  - a group with no members.

## The next-id seam (`d2mapentity/entity_id.go`, `d2mapengine/entity_id.go`)

- **`MapEngine.SetNextEntityID(id)` is the one a load calls.** It refuses an
  id already on the map, because `AddEntity` keys on the id and would
  silently replace the first entity. Then it passes the id to the factory's.
- **`MapEntityFactory.SetNextEntityID(id)`** refuses, with `ErrEntityID` and
  not a panic:
  - `""` and `"player"`;
  - an id while another is still waiting;
  - an id the seam has already used.
- **Every constructor that makes a map entity consumes the waiting id, as its
  first statement** (plan: "every constructor that calls newMapEntity").
  - `NewNPC` and `NewCreature` WEAR it. They are the kinds a save rebuilds.
  - `NewPlayer`, `NewMissile`, `NewItem` and `NewCastOverlay` SPEND it
    without wearing it. The player's id is his connection's, and the other
    three are not saved. Wearing it would be worse than losing it: the engine
    map and the notice model would then hold a monster's saved name on a
    missile.
  - `NewObject` does not call `newMapEntity` and is never saved, so it took
    no part. **The review fixes changed that** (B6): it mints its id with an
    inline `uuid.New`, so an object built while an id waited left it for the
    next monster; it now SPENDS a waiting id like the other unsaved kinds.
  - The id is consumed even when the construction then fails. A consumed id
    counts as used, worn or not.
  - `TestEveryEntityConstructorTakesTheWaitingID` reads the factory's source.
    Every `MapEntityFactory` method that calls `newMapEntity`,
    `newMapEntityWithID`, `NewAnimatedEntity` or `newCreature` must take the
    id in its first statement, so a constructor added later cannot slip past
    the seam. Its positive control is the six names. **Since the review fixes
    it reads TRANSITIVELY** (any chain of the package's own functions that
    reaches `newMapEntity`, `newMapEntityWithID` or an inline `uuid.New`), and
    its positive control is seven names, `NewObject` among them.
- A set id draws nothing from the uuid stream. **But the construction still
  draws from the WORLD stream** (NewCreature a behaviour seed when it stands in
  for a monstat, NewNPC a behaviour seed and one roll per equipment slot:
  `factory.go`), so the load restores the uuid count AND the world RNG after the
  entities (trap 6; corrected at the review, which found the load list here
  restoring neither in the right place). A rebuilt NPC's equipment is
  therefore RE-ROLLED at the load's position of the world stream: a deployed
  model may wear other gear than when saved (the composite's look only).
- `PendingEntityID()` reports what is still waiting.

## Motion (`d2mapentity/motion.go`): `Creature`/`NPC` `.MotionSnapshot()` and `.RestoreMotion(Motion)`

- **Carried:**
  - `pos`, `target`, `velocity`, `path` and `speed`, in raw sub-tiles, so the
    round trip is bit-exact;
  - `dir` (facing), `mode` (the animation mode), `action` (a held mode) and
    `corpse`.
- **Not carried:**
  - the arrival callback: a chase's walk is handed over with none
    (`chaser.Follow` passes nil). **A paced fight's walk is not** (corrected at
    the review): `Game.StepToward` passes `borrowPace`'s return. It needs no
    carrying: saves are refused in a fight, and every frame outside one
    `tacticalAdvance` runs `returnAllPace`, which empties the table the
    callback reads, so the callback is a no-op whenever a save is allowed
    (`TestNoPaceIsBorrowedOutsideAFight`);
  - the animation frame: a held action restarts from its first frame. A
    creature saved while its DEATH is held plays the death again after a load
    and then lies as a corpse; the held action's callback is not carried
    (the game starts every action with a nil one);
  - `drawLayer` and `highlight`, which are render state;
  - an NPC's patrol and its per-NPC RNG: only villagers patrol, and the RNG
    has no effect (plan section 1);
  - the directioner, which is wiring.
- **Velocity** is recomputed by the first step. It is seen only at the load,
  by the renderer's debug overlay, and a test pins that.
- **RestoreMotion** sets the fields directly, never through `setTarget`, which
  would re-derive an NPC's mode. A Motion no entity could have had is refused
  before anything changes.
- **Rule 4 ("a walk you were in the middle of does not continue") is the
  player's alone, and it is a B4 load decision.** There is no MotionSnapshot on
  `*Player`, and B2b implements nothing for it. B4 does not restore his walk:
  he stands at his saved x,y. Monsters, the risen and deployed squads keep
  their motion.

# Review fixes (28 Sep 2026, branch `save-b2-fixes`)

Two independent reviews read B2a and B2b after both merged (master
`ddc3ea7c`). They found one design error that would have made a resumed night
diverge -- trap 4's re-light -- and a set of guards and tests that were weaker
than they looked. Every fix below has a test that was seen RED without it: the
unit controls are N1-N31 (`strigoi-harness-runs\wt-savefix\nc-unit.txt`,
script `nc_unit.py` beside it), the playtest controls P1-P2
(`wt-savefix\playtest-nc-*.txt`). Five decisions were taken by the main
session and implemented here; Josh can overturn any of them.

## The decisions (D1-D5)

**D1 -- trap 4: THE LIGHT MODEL IS THE TRUTH ON LOAD.** The plan said: "a lit
torch's minutes live in the light model and are zero in the kit, so re-light
via the L path and never restore both". Re-lighting would have made a resumed
night diverge three ways: the torch would get a NEW id and move `next_id`; L
is a toggle, so a DOUSED torch (a douse keeps the source and its minutes)
would come back lit; and `ui.torch_verbs` would count a verb the saved game
never made. And the kit is not zero: `saveKit` writes the carried source's
burn into the kit's torch for the sidecar whether it is lit or doused, so the
file holds the minutes twice. So:
- `Light.Restore` restores the snapshot WHOLE, carried source included: id,
  lit, burn, `next_id` exactly (it always did; its doc comment and this file's
  B2a table prescribed the re-light, and now say this).
- B4 zeroes the off-hand torch's `BurnLeft` in the kit it binds whenever the
  light block holds a carried source -- the state the L key leaves the kit in --
  and never presses L. Documented here and in `Light.Restore`; B4a builds it.
- Tests: `TestLightRestoresTheCarriedTorchExactly` (lit and doused: id,
  `next_id`, lit, burn equal, and advancing both copies keeps them equal) and
  d2player's `TestALoadedTorchIsNotRelit` (the controls over the restored model
  have counted no verb, and the next L toggles the SAME source on both, one
  verb each). Controls N23, N23b (restore without the carried source -- the old
  prescription's half -- red in both).

**D2 -- trap 7 against the plan's Light row: A VALUE DERIVED FROM DIALS IS NOT
SAVED; it is re-derived at restore from the dials of the build that loads.**
- `Source.Radius` is the kind's dial (`TorchRadius`, `HearthRadius`). It is no
  longer in `LightSourceSnapshot`; `Light.radiusOf` sets it at `Add` and at
  `Restore`. `TestLightRadiusIsTheDialsNotTheSave` (control N24).
- Soul pressure was `dials.Pressure` plus what the dawns and rites moved,
  saved as one number (`rising.go`: `NewRising` started it at the dial). The
  rising now keeps `accrued` (the dawns and rites) and `Pressure()` adds the
  dial; the snapshot saves `pressure_accrued` only, and the provider reports
  it beside `pressure`. A script's `pressure` write is a dial (it moves the
  constant so the total reads what was written) and is not saved, like every
  harness dial. `TestRisingSavesOnlyTheAccruedPressure` (control N24b).
- The plan's Light row lists "radius" as saved; it should not (for the plan).

**D3 -- squads with deployed models are B4b's.** A deployed squad's models are
map entities, rebuilt with their saved ids through B2b's next-id seam, which is
the hunted-night load's. `Squads.Restore`'s register row (and its Validate
twin's) moved from B4a to B4b. B4a's scope is a quiet evening with no deployed
squad models: its load restores s:1 through `Squads.Restore` and REFUSES a
snapshot holding a deployed squad until B4b. That makes the row go live in
B4a, early; the burst that moves it to wire must show the refusal. Documented
on `Squads.Restore` and in the register.

**D4 -- all-or-nothing load: every Restore has a Validate twin.** On all nine
systems -- Clock, Light, Squads, Corpses, Rising, Combat, Spawns, Notice,
Pursuit -- `Validate(snap[, ...])` runs every check Restore runs and changes
nothing, and each Restore calls its Validate first, so the two cannot
disagree. The signatures: `Clock/Light/Squads/Corpses.Validate(snap)`,
`Rising.Validate(snap, worldSeed, bodies CorpsesSnapshot)` (it reads the
FILE's corpses, since the registry is still empty when a load validates),
`Combat.Validate(snap, worldSeed)`, `Spawns.Validate(snap, r, worldSeed)`,
`Notice/Pursuit.Validate(snap, r)`. The load validates every block, then
restores every block, and any refusal tears the whole game down and falls back
per rule 7 (the load order below). Control N22 (Corpses.Validate reduced to
its emptiness check: red); every refusal test calls both where it can.

**D5 -- rule 8 against exact positions: decided for B4b, documented, no code.**
If the map's SHA matches the file's, positions must match exactly (today's
check: a member must resolve to an entity standing where he was saved). If the
SHA differs, the world file is SET ASIDE with a message and he begins at dawn
(rule 7's path), rather than half-restoring packs on a changed map. **This
narrows plan rule 8** ("if the village has been rearranged since you saved,
the save still loads") **to the hero only**: on a rearranged village his
hero, kit and progress still load, at dawn; the night he saved in does not.
A decision for Josh to see.

## The B4 load order -- the one authoritative list

It replaces the plan's section 5 list, B2a's per-system notes above and B2b's
"What B4b must do on load" (which put the villagers after the entities and
left the world RNG out). B4a builds the steps that name no entity; B4b the
rest.

1. **Before `Open`.** Read the file; a version other than 1 is refused (rule
   7). Decode every seed as an int64 (B1 notes section 2). Refuse in a network
   game -- rule 9 refuses LOADS as well as saves (the TCP handlers race the
   counted world stream, C13). Compare the map's SHA (D5): different -> set
   the file aside, begin at dawn. `SetNextGameSeed(file seed)`,
   `SetNextStartPosition(hero x, y)`. Write the embedded sidecar blocks, with
   the off-hand torch's `BurnLeft` ZEROED when the light block holds a carried
   source (D1).
2. **In `CreateGame`, the clock: Validate, then Restore, right after
   `NewClock`** (trap 1). It is the one block restored before the others are
   validated, because every system built after it samples it; it checks
   itself first, and a later refusal still tears the whole game down (step 8).
3. **In `bindGameControls`, after `bindKit`: rebuild the world's entities.**
   Villager re-ids first (the plan's order; the verb that re-keys an entity
   does not exist yet, B4b). Then each saved entity (B4b): the engine's
   `SetNextEntityID(id)`, build its kind (`NewCreature`/`NewNPC`), check
   `ID() == id` (a mismatch refuses the file), `RestoreMotion` (refuses a
   Motion no entity could have had), `AddEntity`. Then assert
   `PendingEntityID()` is empty. Deployed squad models are among these
   entities (D3).
4. **VALIDATE EVERY BLOCK (D4)**, through ONE Resolver built over the resumed
   map: Light, Squads (B4a: refuse a deployed squad), Corpses, Rising (against
   the file's corpses), Combat, Spawns, Notice, Pursuit, the game spawner's
   arrival, every saved stream (`StreamState.Check(fileSeed, name)`, the
   world's under `StreamWorld`), the hero's health, the scene. Nothing has
   been restored but the clock.
5. **RESTORE EVERY BLOCK**, in this order: player health (after
   `applyProgress`); squads; light, WHOLE (D1); corpses WITHOUT the `changed`
   callback, `placeTheDead` skipped (trap 5); rising (after the corpses);
   spawns, which puts the tables' stream back, then the spawner's arrival;
   notice; pursuit; combat; the scene, `lastStage` and `dawnPaidDay` together
   from the file (trap 1, BUG-17). He stands at his saved x, y: his walk is not
   restored (rule 4).
6. **THE WORLD RNG AND THE uuid STREAM, AFTER the entities** (trap 6):
   `MapEngine.RestoreRand(seed, draws)` -- NewCreature and NewNPC drew from the
   world stream in step 3 -- and, in a harness build, the uuid stream's byte
   count (`RestoreReader`), on BOTH paths: a fresh launch and the death
   screen's in-process "load last save" (B1 notes section 1).
7. **Harness only: re-apply the dials a script set**, which are never saved.
8. **Any refusal, at any step from 1 to 6, tears the whole game down** --
   the client closed, the world released -- sets the file aside with the
   reason, and falls back per rule 7: he begins at dawn from his sidecar. A
   half-restored world never runs a frame.

## Reading it: `d2save.Decode` (what B4's step 1 calls)

In order, refusing anything a load could not restore exactly:

1. Not a JSON object: `ErrWorldFile`.
2. `version` not the integer literal `1` -- `2`, `0`, `-1`, `"1"`, `1.0`,
   `null`, or absent -- is a `*VersionError` naming it, which `errors.Is`
   `ErrWorldVersion`, and nothing else is read. `VersionOf(data)` reads only
   the version.
3. A block missing, `null`, or not one of `Blocks`: `ErrWorldFile`. **A missing
   block is never an empty system.**
4. A field this build does not know, at any depth: `ErrWorldFile`
   (`DisallowUnknownFields`).
5. `World.Check` (next section).

Seeds decode through typed `int64` fields, never float64
(`TestSeedsPast2To53Survive` at 2^62+12345: exact typed, and an exact string
to a float64 reader, where the same number as a JSON number reads another
seed).

## `World.Check`: the file's own refusals

Everything the file can refuse with no game to hand (the systems' own checks,
each B2 `Validate`, need the game the load builds: B4, D4):

- `map`: generated XOR (path and a 64-hex sha).
- `rng`: each copy equals its block's stream; each of the four streams passes
  `d2rand.StreamState.Check(seed, name)` (on the seed's stream, at most
  `MaxDraws`) -- so a swapped pair is refused.
- `hero`: finite; `x, y` exactly `d2vector.Position.World()` of `pos`; health
  above 0 (a dead hero is never saved).
- `sidecar`: an object of version 1 with a kit.
- `clock`: finite, not negative.
- `entities`: ids unique, sorted, never `""` or `player`; `npc` names a
  monstat and no creature, `creature` the reverse; `native` iff `born`;
  finite; `x, y` exactly the world point of `motion.pos`.
- `bodies`: unique, sorted, each an entity in the list, `0 <= health <= max`,
  `max >= 1`.
- LIVE REFERENCES: every spawns member not `gone` is an entity standing
  EXACTLY at the member's `x, y`; a `gone` member is NOT an entity; every
  watcher, watch target, hunter, quarry and deployed squad model is an entity
  or the word `player`. (The corpse registry's maps are history, not live
  references, and are not checked.)
- `scene`: finite, `watch_stood >= 0`, `last_stage` a stage.

`SaveWorld` runs `Check` on the world before encoding and `Decode` on the bytes
before writing: **strict at save** -- a file no load could read is never
written over the player's save.

## Writing it: `d2save.WriteWorld`

- A version-1 file already at the path is the previous save: copied to
  `.bak` (`d2items.KeepGeneration`), rule 5.
- A file of any other version, or not a world file at all, is one this build
  cannot read; rule 7 says it is never overwritten: it is MOVED to
  `.v<N>.unread` (a whole-number version) or `.unread` (anything else), under
  a numbered suffix (`.1`, `.2`...) if that name is taken, so a second never
  overwrites the first. `.bak` is left alone. (Decision B3-7: this happens at
  SAVE too, not only at load -- until B4 exists, a newer build's file could
  sit there when an older build saves.)
- Then `d2items.WriteFileAtomic`: a temporary file and a rename, retried while
  Windows holds the target.

The `.od2` now writes the same way (`HeroStateFactory.Save`: `.bak`, then tmp +
rename; BUG-48). The sidecar has NO `.bak`: it is rewritten on every equip,
level and fight's end, so its "previous generation" would be the last equip,
not the last save -- and the world file carries its own copy, so `world.bak`
is the previous save whole (decision B3-11).

## The verb: `Game.SaveWorld(SaveOptions)` (`d2game/d2gamescreen/save.go`)

1. **Arguments**: `omit` without `to` is refused (`errOmitNeedsTo`).
2. **Refusals** (a `*SaveRefusal`, `errors.Is` `ErrSaveRefused`; NO file is
   touched -- nothing has been read or written yet), in this order:
   - `NOT_READY`: no game; `NETWORK` (rule 9: the TCP handlers race the
     counted world stream); `NOT_READY`: no hero save opened, or no hero in
     the world yet;
   - `DEAD`: `died` or his body at 0 (checked BEFORE the fight: a man who died
     in a fight is `DEAD`);
   - `FIGHTING`: a fight running (`Combat.Fighting`), a paced fight holding the
     world (`WorldHeld`), the fight edge not yet taken back (`wasFighting`), a
     strike waiting on a walk (`pendingStrike`), a tactical pace or tile still
     out, or the journal still reading a fight (`journalFight`) -- and, after
     these, `Combat.Snapshot`'s own refusal (experience or paced minutes not
     yet taken, the pace window open) is `FIGHTING` too;
   - `TALKING`: `talk != nil` (a talk that reaches its end is ended by
     `Answer` at once, so this is "a talk is open"). A sleep's shelter is set
     only inside one answer's call and can never be seen by a caller, so it
     is not a refusal of its own (decision B3-10);
   - `JOURNAL`, `LOADOUT`;
   - `NOT_READY`: no kit (he has never chosen), or a world system missing.
3. **Snapshots**, every one a read: every B2 `Snapshot`, through ONE Resolver
   over the live map for spawns, notice and pursuit (`worldResolver`: an
   entity id is that entity wrapped as the live path wraps it -- `chaser` --
   and `player` is `prey{localPlayer}`; **B4b's load must build its Resolver
   the same way**), the sidecar bytes (`heroBytes`, the one document
   `saveKit` also writes now), the bodies, the entities, the scene, the map.
4. `World.Check`, `Encode(omit)`, and (without omit) `Decode` of the bytes.
5. With `to`: write ONLY the world file there, and stop (decision B3-3).
6. Otherwise: **the world file** (`WriteWorld`), then **his `.od2`**
   (`OnPlayerSave` -> the server's save, synchronous for a local client; its
   error now comes back, BUG-49), then **his sidecar** (the SAME bytes), then
   **the death screen's copy re-taken** (`snapshotHero`), so "load last save"
   after a death means this moment in all three files. A failure part-way
   says which files are written ("the world file is written and his .od2 is
   not"); the `.bak`s hold the save before.

**It changes nothing in the world.** No stream is drawn, no minute passes, no
system advances; the one thing a save moves is the death screen's copy.
`TestSaveResume` 7a and 7c: the state digest before and after is one digest;
control P1 (one draw from the world stream) is red on `[systems rng]`.

**It is not in `OnUnload`** and cannot be: `OnUnload` releases every world
system and nils the bodies before its `.od2` save. `OnUnload` is unchanged but
for one thing: a failed `.od2` save is logged and the unload goes on (the kit's
save, the client's close) instead of returning early (BUG-49).

## Decisions (the recommended option taken each time; Josh can overturn any)

- **B3-1, `rng` holds copies.** The plan lists `rng {world, spawns, combat,
  rising, uuid?}` while B2 put each gameplay stream inside its own block.
  Taken: both, and `Check` refuses a file where a copy and its block
  disagree, so the copy can never be a second truth; `rng` is the one place a
  load reads to check every stream. (Alternative: `rng {world, uuid?}` only.)
- **B3-2, `scene.watch_clock` is saved**, against the plan's "D". Measured by
  reading `keepWatch`: a labour verb moves the clock inside a frame and the
  next frame credits the jump (capped at `watchJumpMinutes`); a save in
  between that derived the clock would credit nothing. With the menu or the
  dawn that gap cannot be hit; with a paused harness it can.
- **B3-3, `to` writes only the world file**, and `omit` needs `to`: a file
  with a block missing never replaces his save, and a negative control's file
  is a whole save of the moment (it embeds the sidecar).
- **B3-4, the sidecar is embedded whole** (its `version` too), the same bytes
  the sidecar file gets.
- **B3-5, positions twice where the load must be exact**: world tiles to read
  and compare (`x`, `y`), sub-tiles to restore (`pos`, `motion.pos`), held
  equal by `Check`.
- **B3-6, native = on the map when the screen is made.** B4b re-keys them by
  (`name_key`, `born`). A native that died and was taken off the map is simply
  absent from the list; B4b must remove what the map rebuilds and the file
  does not have. Natives carry their motion, but an NPC's patrol (path index,
  repetitions) is not carried (B2b: "only villagers patrol"), so a villager
  resumes his walk, not his patrol's count -- B4b's call.
- **B3-7, set aside at save as well as at load** (above).
- **B3-8, any change to a snapshot's JSON shape bumps `Version`.** Decode
  refuses unknown fields but NOT a missing nested field (it would read zero):
  a file from before a field existed would load that field as zero. There is
  no migration (plan section 6), so an added field is an incompatible change.
- **B3-9, refusal order**: arguments, readiness and network, `DEAD`, then
  `FIGHTING`, `TALKING`, `JOURNAL`, `LOADOUT`.
- **B3-10, `TALKING` is `talk != nil`**; the shelter needs no refusal.
- **B3-11, no sidecar `.bak`** (above).
- **B3-12, a failed `.od2` save is an error to its sender** (BUG-49), and
  `OnUnload` logs it and goes on.
- **B3-13, the register**: `SaveWorld`, every B3 Snapshot row and the d2save
  verbs are HARNESS-ONLY until B5 gives the save its game callers; `Decode`
  and `World.Check` until B4a's load. What the game already calls is wire:
  `KeepGeneration` (every hero save), `HeroBytes` (every kit save),
  `Creature.SetCreatureID` (every creature the spawner places).
- **B3-14, a script's `strigoi_reseed_world` makes every later save refuse**
  (`INTERNAL`: the world stream is no longer on the game's seed, which no load
  could restore). Harness only; the game never reseeds mid-game.
