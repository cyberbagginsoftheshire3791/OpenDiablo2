# M4.6 world save: carry-overs from B1's review

Short, and owned. Each entry below is something burst B1 (the counted streams
and the observed fields, branch `save-b1`) found and did NOT build, with the
later burst that owns it. Written 27 Sep 2026 after an independent review of
B1; the build plan itself is the main session's.

## 1. "Load last save" is not a seeded game (owner: B4b)

Only `strigoi_start_game` seeds a game. It sets the server's one-shot seed
(`d2server.SetNextGameSeed`) and reseeds the harness's uuid stream
(`d2app/harness_uuid.go`), then begins the game. The death screen's "load last
save" goes `App.ReloadGame` -> main menu -> `ToCreateGame` (`d2app/reload.go`)
and does neither, so the reloaded game, in a process that was seeded:

- takes a **wall-clock server seed**: `takeNextGameSeed` is one-shot and the
  first game consumed the override. The world RNG, the spawn tables, combat and
  the rising all seed from `gameClient.Seed`, so all four start where no script
  chose;
- **continues the uuid stream** from the dead game's byte count: its player id
  (the connection's uuid) and every entity id are the seed's later ids;
- therefore matches **no fresh launch**. It is deterministic only for the same
  script in the same process.

How to see it: the `uuid` provider reports `seeded_for_this_game` (false on a
reloaded game), `games` (= `seeded_game + 1` there) and `bytes_at_game_start`
(the dead game's count); every stream's `rng.seed_str` shows the wall-clock
seed. Pinned as it is today by `d2app` `TestUUIDStreamOnAFreshLaunchAndOnAReload`
(both halves) and `TestTownWalkDeterministic` (the fresh half).

**B4b** restores these on a load: the server seed from the save, and the uuid
stream with `d2rand.RestoreReader(seed, bytes)` AFTER the entities are rebuilt
(the plan's trap 6). When it does, the reload half of the unit test changes
with it, on purpose.

## 2. Seeds are int64; decode them as int64 (owner: B2, the world file)

A wall-clock seed (UnixNano, ~1.8e18) is past 2^53, where float64 stops
holding every integer. A reader that decodes JSON into float64 -- every
playtest's `mustNum` does -- reads a DIFFERENT seed, and a stream restored from
it is a different stream from its first value. So every stream report carries
`seed_str` (exact decimal) beside `seed`, and **the world file must decode
seeds as int64** (`json.Decoder.UseNumber` then `Int64`, or a typed struct
field), never through `interface{}`/float64. `d2rand`
`TestSeedStrSurvivesAFloat64Decoder` shows the loss and both exact routes.

## 3. A stream is one value (done in B1; for B2's Restore)

Spawns, Combat and Rising each hold one `*d2rand.Stream` (the `*rand.Rand` and
its counted source), and `Stream.Restore(seed, draws)` replaces both at once.
B2's system Restore calls that and nothing else (through
`d2rand.StreamState.RestoreInto` since the B2 review, after
`StreamState.Check` has refused a stream on another stream's seed or past
`MaxDraws`). Do not take `.Rand` out of a
stream and keep it: after a Restore it draws from the old, uncounted source.
The map engine is the exception, because its stream is handed to two factories:
`MapEngine.RestoreRand` goes through `useRand`, which re-hands it, and
`TestRestoreRandHandsTheStreamToTheFactories` holds it there.

## 4. A pack's members include its dead (for B2's snapshot)

`group.members` is never shortened: a death unwatches its member (combat's
`withdraw`) and the group keeps him, and the game reads the dead there --
`spent()` is "no member still watched" over the whole list, a dead man's
profile still names his pack, and a despawn takes every member off the map. `spawns.group_list[].member_ids` reports every
member as placed, dead ones included; the `notice` rows are only the watched.
The snapshot must carry `member_ids`, not the notice rows.

# B2a: the snapshots with no entity ids (branch `save-b2a`, 27 Sep 2026)

Six systems gained `Snapshot()` and `Restore()`, each in
`d2core/d2world/<system>_snapshot.go` with JSON tags, and each closed by its
`_snapshot_test.go` five ways (the shared helpers are in
`d2core/d2world/b2a_sweep_test.go`, all named `b2a*`):

1. **Round trip.** Snapshot, through JSON, into a FRESH system: the provider
   and the behaviour cannot tell the copy from the original.
2. **Run on.** Both advanced by the same steps stay equal (the provider, and
   whatever else the game reads: levels, bars, blows, bodies).
3. **The sweep.** Every leaf of the snapshot zeroed (or, if already zero, set),
   every list element and object key dropped, one at a time, restored and run
   on: each variant must be REFUSED by Restore or DIVERGE from the original.
   One that does neither fails the test ("losing it changed nothing
   observable"). The only exemptions are named with their reason, must stay
   silent, and must be reached. The first read is taken before the first step:
   what a load shows on its first frame is the save's to get right. **The
   sweep restores the untouched snapshot first**, the same way as every
   variant, and fails unless that matches the original: otherwise a sweep
   whose restore path differs from the original's (a binding in another
   order, a step missed) sees every variant diverge and passes having proved
   nothing (added 28 Sep; see "The finish" below).
4. **Classification.** Every field of every runtime struct a snapshot covers
   is listed as S (saved, with the JSON path it is saved at), D (derived on
   load), T (transient: empty whenever a save is allowed) or W (wiring). A
   field added later fails the test until someone classifies it.
5. **The probes** (`b2aMustDiverge`, added 28 Sep). The sweep counts a refused
   variant as its field seen, but for a field Restore CHECKS -- an id, a next
   id, a count tied to another count -- a refusal proves the check, not that
   the field matters: lost consistently, nothing would refuse. So each such
   field gets a valid-but-wrong value (a fresh model's ids and counts, a next
   id one past the last, another stage, another squad selected, a body
   renamed), which Restore must ACCEPT and the run on must DIVERGE from.

Every Restore is checked whole before it changes anything, so a refused
snapshot leaves the system as it was.

**The streams.** Rising and Combat save their stream as `{seed, draws}` and

## C6: one seed per stream (done in B2a)

`d2rand.Derive(seed, name)` gives the spawn tables, combat and the rising
each its own seed; the world stream keeps the game seed, so the map and the
digest's world part do not move. It works in math/rand's residue space
(`rngSource.Seed` reduces every seed modulo 2^31-1, and two seeds with one
residue are ONE stream), moving the game's effective seed by a fixed
per-name offset (FNV-1a) around the ring of non-zero residues. So for any game
seed the four streams are four different streams -- guaranteed, not merely
likely -- and every derived seed is below 2^31. At seed 1462: spawns
443254809, combat 179919329, rising 1368529044 (pinned by `TestDeriveIsFixed`).

This changes every seeded fight and night once (the rising already had its own
stream, at seed+4707, and now has a derived one). Three scripts were keyed to
an outcome of the old dice; each was re-measured, and each fix also passes on
the old seeding:

- **TestSpawns act 6c** checked the streams' seeds against the old seeding. It
  now checks each against `Derive`, exactly and as `seed_str`, and that all
  four differ. Seen red with combat put back on the game seed.
- **TestCombatResolver act 4** needs the dog dead ("the corpse has no bar").
  Acts 2 and 3 used to kill it on the old dice; on the new ones it stands with
  12 of 61. The script now finishes it with forced crits and fails if eight do
  not -- a corpse is the act's premise, not its finding.
- **TestTacticalFight act 3's control** clicked while his riposte swing was in
  flight (on the new dice the zombie grazes him and he ripostes), and a click
  during a swing is swallowed by the `IsCasting` gate with no notice. The
  control now waits the swing out, as a person would.

**The unaided man's numbers moved** (history 122's winnability measurements
were taken on the old streams). `TestTheUnaidedChain` at seed 1462: old
seeding, he dies at 21:59 with two aware at the peak; new seeding, at 22:29
with one. One encounter either way.

# B2b: the snapshots that carry entity ids (branch `save-b2b`, 28 Sep 2026)

Three world systems that point at entities -- Spawns, Notice and Pursuit --
gained `Snapshot(r)` and `Restore(snap, r)` through a `Resolver`. The game
spawner gained its own small pair, the entity factory gained the next-id seam,
and creatures and NPCs gained a motion snapshot. Nothing in the game calls
any of it yet: B3 writes the snapshots, B4b restores them.

The work was started on 27 Sep and cut off before review or gate. It was then
inherited, audited field by field against build plan section 5, fixed, and
closed on 28 Sep. "What the audit changed" below lists what the first draft
got wrong.

## The Resolver (`d2core/d2world/resolver.go`)

```go
type Resolver interface {
	Watcher(id string) (Watcher, bool) // the live entity with this id
	Quarry(ref string) (Quarry, bool)  // PlayerRef is the player; else an entity id
}
const PlayerRef = "player"
```

- **No remap table.** Every entity comes back with its saved id (the seam
  below), so a Resolver is a lookup, not a translation. The player is the one
  exception: his id is his connection's uuid and is new every launch. So every
  record that points at him is written as the word `player`.
- **Strict at load.** An id that does not resolve is `ErrUnresolvedRef`, never
  a silent drop. So is an id that resolves to something answering to another
  id. A chase's hunter must also be a `Hunter`, which is the type assertion
  `startChasesForTheAware` makes on the live path.
- **Strict at save.** `Snapshot(r)` takes a Resolver over the LIVE world:
  - it names the player through it. If there is a watch or a chase and no
    player, the snapshot is refused;
  - every ref it writes must resolve now, so a file no load could read is
    refused before it is written.
- **All-or-nothing.** Every Restore checks the whole snapshot before it
  changes anything, so a refused one leaves the system exactly as it was.
- The shared helpers sit beside the interface (`b2bResolveWatcher`,
  `b2bResolveQuarry`, `b2bLivePlayerID`, `b2bSavedRefsResolve`,
  `b2bCheckNumbers`). All are B2b-private. There is no shared `snapshot.go`.
- **The game's Resolver is B4b's to write.** It must be built over
  `MapEngine.Entities()`, and it must return the same adapter the live path
  builds: a `chaser` wrapping the entity, with `Quarry(PlayerRef)` giving
  `prey{localPlayer}`. The save and the load must use the same Resolver type.

**Members** are saved as `{id, x, y, gone}`, and the dead are included (B1's
`member_ids`).

- **A member on the map** must resolve at load, to an entity standing EXACTLY
  at the saved x,y. The position is an identity check, not a second copy of
  his motion. The wrong entity is refused, and so is one whose motion was not
  restored first.
- **A gone member** was in his group and not on the map at save: a slain man
  whose body stood up, so `takeOffTheMap` took his remains.
  - Gone is decided at save by the live Resolver, then **checked against the
    notice model**. A death unwatches a man (`Combat.withdraw`) before
    anything takes him off the map. So a member the Resolver cannot find
    while notice still watches him is a living wolf the Resolver lost, not a
    dead man, and the save is refused.
  - At load a gone member must NOT resolve. He comes back as a stand-in
    (`b2bGoneMember`) that answers with his id and his last place, which is
    all the game ever asks of him.
  - His x,y is carried and nothing reads it. The sweep pins that as
    `carried`, so it goes red the day something reads it.
- **Refused at load:**
  - a group id that is not `g:<n>` below `next_id`;
  - a row this build's tables do not have;
  - a band outside -1..2, or an unknown stage name;
  - a non-finite number, or a negative count;
  - an id saved twice;
  - a group with no members.

## The next-id seam (`d2mapentity/entity_id.go`, `d2mapengine/entity_id.go`)

- **`MapEngine.SetNextEntityID(id)` is the one a load calls.** It refuses an
  id already on the map, because `AddEntity` keys on the id and would
  silently replace the first entity. Then it passes the id to the factory's.
- **`MapEntityFactory.SetNextEntityID(id)`** refuses, with `ErrEntityID` and
  not a panic:
  - `""` and `"player"`;
  - an id while another is still waiting;
  - an id the seam has already used.
- **Every constructor that makes a map entity consumes the waiting id, as its
  first statement** (plan: "every constructor that calls newMapEntity").
  - `NewNPC` and `NewCreature` WEAR it. They are the kinds a save rebuilds.
  - `NewPlayer`, `NewMissile`, `NewItem` and `NewCastOverlay` SPEND it
    without wearing it. The player's id is his connection's, and the other
    three are not saved. Wearing it would be worse than losing it: the engine
    map and the notice model would then hold a monster's saved name on a
    missile.
  - `NewObject` does not call `newMapEntity` and is never saved, so it took
    no part. **The review fixes changed that** (B6): it mints its id with an
    inline `uuid.New`, so an object built while an id waited left it for the
    next monster; it now SPENDS a waiting id like the other unsaved kinds.
  - The id is consumed even when the construction then fails. A consumed id
    counts as used, worn or not.
  - `TestEveryEntityConstructorTakesTheWaitingID` reads the factory's source.
    Every `MapEntityFactory` method that calls `newMapEntity`,
    `newMapEntityWithID`, `NewAnimatedEntity` or `newCreature` must take the
    id in its first statement, so a constructor added later cannot slip past
    the seam. Its positive control is the six names. **Since the review fixes
    it reads TRANSITIVELY** (any chain of the package's own functions that
    reaches `newMapEntity`, `newMapEntityWithID` or an inline `uuid.New`), and
    its positive control is seven names, `NewObject` among them.
- A set id draws nothing from the uuid stream. **But the construction still
  draws from the WORLD stream** (NewCreature a behaviour seed when it stands in
  for a monstat, NewNPC a behaviour seed and one roll per equipment slot:
  `factory.go`), so the load restores the uuid count AND the world RNG after the
  entities (trap 6; corrected at the review, which found the load list here
  restoring neither in the right place). A rebuilt NPC's equipment is
  therefore RE-ROLLED at the load's position of the world stream: a deployed
  model may wear other gear than when saved (the composite's look only).
- `PendingEntityID()` reports what is still waiting.

## Motion (`d2mapentity/motion.go`): `Creature`/`NPC` `.MotionSnapshot()` and `.RestoreMotion(Motion)`

- **Carried:**
  - `pos`, `target`, `velocity`, `path` and `speed`, in raw sub-tiles, so the
    round trip is bit-exact;
  - `dir` (facing), `mode` (the animation mode), `action` (a held mode) and
    `corpse`.
- **Not carried:**
  - the arrival callback: a chase's walk is handed over with none
    (`chaser.Follow` passes nil). **A paced fight's walk is not** (corrected at
    the review): `Game.StepToward` passes `borrowPace`'s return. It needs no
    carrying: saves are refused in a fight, and every frame outside one
    `tacticalAdvance` runs `returnAllPace`, which empties the table the
    callback reads, so the callback is a no-op whenever a save is allowed
    (`TestNoPaceIsBorrowedOutsideAFight`);
  - the animation frame: a held action restarts from its first frame. A
    creature saved while its DEATH is held plays the death again after a load
    and then lies as a corpse; the held action's callback is not carried
    (the game starts every action with a nil one). **Corrected by the B4b
    review fixes (29 Sep 2026; BUG-75, BUG-76): "and then lies as a corpse, as
    it would have" was untrue.** The death ended later than it would have,
    and a monster slain while it walked walked on through its death, so its
    corpse came to rest further along its route. A death now ends the walk
    where it begins, and no held action is saved or loaded: the save refuses
    while one plays, the load refuses a file that holds one. See "B4b review
    fixes" at the end of this file;
  - `drawLayer` and `highlight`, which are render state;
  - an NPC's patrol and its per-NPC RNG: only villagers patrol, and the RNG
    has no effect (plan section 1);
  - the directioner, which is wiring.
- **Velocity** is recomputed by the first step. It is seen only at the load,
  by the renderer's debug overlay, and a test pins that.
- **RestoreMotion** sets the fields directly, never through `setTarget`, which
  would re-derive an NPC's mode. A Motion no entity could have had is refused
  before anything changes.
- **Rule 4 ("a walk you were in the middle of does not continue") is the
  player's alone, and it is a B4 load decision.** There is no MotionSnapshot on
  `*Player`, and B2b implements nothing for it. B4 does not restore his walk:
  he stands at his saved x,y. Monsters, the risen and deployed squads keep
  their motion.

# Review fixes (28 Sep 2026, branch `save-b2-fixes`)

Two independent reviews read B2a and B2b after both merged (master
`ddc3ea7c`). They found one design error that would have made a resumed night
diverge -- trap 4's re-light -- and a set of guards and tests that were weaker
than they looked. Every fix below has a test that was seen RED without it: the
unit controls are N1-N31 (`strigoi-harness-runs\wt-savefix\nc-unit.txt`,
script `nc_unit.py` beside it), the playtest controls P1-P2
(`wt-savefix\playtest-nc-*.txt`). Five decisions were taken by the main
session and implemented here; Josh can overturn any of them.

## The decisions (D1-D5)

**D1 -- trap 4: THE LIGHT MODEL IS THE TRUTH ON LOAD.** The plan said: "a lit
torch's minutes live in the light model and are zero in the kit, so re-light
via the L path and never restore both". Re-lighting would have made a resumed
night diverge three ways: the torch would get a NEW id and move `next_id`; L
is a toggle, so a DOUSED torch (a douse keeps the source and its minutes)
would come back lit; and `ui.torch_verbs` would count a verb the saved game
never made. And the kit is not zero: `saveKit` writes the carried source's
burn into the kit's torch for the sidecar whether it is lit or doused, so the
file holds the minutes twice. So:
- `Light.Restore` restores the snapshot WHOLE, carried source included: id,
  lit, burn, `next_id` exactly (it always did; its doc comment and this file's
  B2a table prescribed the re-light, and now say this).
- B4 zeroes the off-hand torch's `BurnLeft` in the kit it binds whenever the
  light block holds a carried source -- the state the L key leaves the kit in --
  and never presses L. Documented here and in `Light.Restore`; B4a builds it.
- Tests: `TestLightRestoresTheCarriedTorchExactly` (lit and doused: id,
  `next_id`, lit, burn equal, and advancing both copies keeps them equal) and
  d2player's `TestALoadedTorchIsNotRelit` (the controls over the restored model
  have counted no verb, and the next L toggles the SAME source on both, one
  verb each). Controls N23, N23b (restore without the carried source -- the old
  prescription's half -- red in both).

**D2 -- trap 7 against the plan's Light row: A VALUE DERIVED FROM DIALS IS NOT
SAVED; it is re-derived at restore from the dials of the build that loads.**
- `Source.Radius` is the kind's dial (`TorchRadius`, `HearthRadius`). It is no
  longer in `LightSourceSnapshot`; `Light.radiusOf` sets it at `Add` and at
  `Restore`. `TestLightRadiusIsTheDialsNotTheSave` (control N24).
- Soul pressure was `dials.Pressure` plus what the dawns and rites moved,
  saved as one number (`rising.go`: `NewRising` started it at the dial). The
  rising now keeps `accrued` (the dawns and rites) and `Pressure()` adds the
  dial; the snapshot saves `pressure_accrued` only, and the provider reports
  it beside `pressure`. A script's `pressure` write is a dial (it moves the
  constant so the total reads what was written) and is not saved, like every
  harness dial. `TestRisingSavesOnlyTheAccruedPressure` (control N24b).
- The plan's Light row lists "radius" as saved; it should not (for the plan).

**D3 -- squads with deployed models are B4b's.** A deployed squad's models are
map entities, rebuilt with their saved ids through B2b's next-id seam, which is
the hunted-night load's. `Squads.Restore`'s register row (and its Validate
twin's) moved from B4a to B4b. B4a's scope is a quiet evening with no deployed
squad models: its load restores s:1 through `Squads.Restore` and REFUSES a
snapshot holding a deployed squad until B4b. That makes the row go live in
B4a, early; the burst that moves it to wire must show the refusal. Documented
on `Squads.Restore` and in the register.

**D4 -- all-or-nothing load: every Restore has a Validate twin.** On all nine
systems -- Clock, Light, Squads, Corpses, Rising, Combat, Spawns, Notice,
Pursuit -- `Validate(snap[, ...])` runs every check Restore runs and changes
nothing, and each Restore calls its Validate first, so the two cannot
disagree. The signatures: `Clock/Light/Squads/Corpses.Validate(snap)`,
`Rising.Validate(snap, worldSeed, bodies CorpsesSnapshot)` (it reads the
FILE's corpses, since the registry is still empty when a load validates),
`Combat.Validate(snap, worldSeed)`, `Spawns.Validate(snap, r, worldSeed)`,
`Notice/Pursuit.Validate(snap, r)`. The load validates every block, then
restores every block, and any refusal tears the whole game down and falls back
per rule 7 (the load order below). Control N22 (Corpses.Validate reduced to
its emptiness check: red); every refusal test calls both where it can.

**D5 -- rule 8 against exact positions: decided for B4b, documented, no code.**
If the map's SHA matches the file's, positions must match exactly (today's
check: a member must resolve to an entity standing where he was saved). If the
SHA differs, the world file is SET ASIDE with a message and he begins at dawn
(rule 7's path), rather than half-restoring packs on a changed map. **This
narrows plan rule 8** ("if the village has been rearranged since you saved,
the save still loads") **to the hero only**: on a rearranged village his
hero, kit and progress still load, at dawn; the night he saved in does not.
A decision for Josh to see.

## Reading it: `d2save.Decode` (what B4's step 1 calls)

In order, refusing anything a load could not restore exactly:

1. Not a JSON object: `ErrWorldFile`.
2. `version` not the integer literal `1` -- `2`, `0`, `-1`, `"1"`, `1.0`,
   `null`, or absent -- is a `*VersionError` naming it, which `errors.Is`
   `ErrWorldVersion`, and nothing else is read. `VersionOf(data)` reads only
   the version.
3. A block missing, `null`, or not one of `Blocks`: `ErrWorldFile`. **A missing
   block is never an empty system.**
4. A field this build does not know, at any depth: `ErrWorldFile`
   (`DisallowUnknownFields`).
5. `World.Check` (next section).

Seeds decode through typed `int64` fields, never float64
(`TestSeedsPast2To53Survive` at 2^62+12345: exact typed, and an exact string
to a float64 reader, where the same number as a JSON number reads another
seed).

## `World.Check`: the file's own refusals

Everything the file can refuse with no game to hand (the systems' own checks,
each B2 `Validate`, need the game the load builds: B4, D4):

- `map`: generated XOR (path and a 64-hex sha).
- `rng`: each copy equals its block's stream; each of the four streams passes
  `d2rand.StreamState.Check(seed, name)` (on the seed's stream, at most
  `MaxDraws`) -- so a swapped pair is refused.
- `hero`: finite; `x, y` exactly `d2vector.Position.World()` of `pos`; health
  above 0 (a dead hero is never saved).
- `sidecar`: an object of version 1 with a kit.
- `clock`: finite, not negative.
- `entities`: ids unique, sorted, never `""` or `player`; `npc` names a
  monstat and no creature, `creature` the reverse; `native` iff `born`;
  finite; `x, y` exactly the world point of `motion.pos`.
- `bodies`: unique, sorted, each an entity in the list, `0 <= health <= max`,
  `max >= 1`.
- LIVE REFERENCES: every spawns member not `gone` is an entity standing
  EXACTLY at the member's `x, y`; a `gone` member is NOT an entity; every
  watcher, watch target, hunter, quarry and deployed squad model is an entity
  or the word `player`. (The corpse registry's maps are history, not live
  references, and are not checked.)
- `scene`: finite, `watch_stood >= 0`, `last_stage` a stage.

`SaveWorld` runs `Check` on the world before encoding and `Decode` on the bytes
before writing: **strict at save** -- a file no load could read is never
written over the player's save.

## Writing it: `d2save.WriteWorld`

- A version-1 file already at the path is the previous save: copied to
  `.bak` (`d2items.KeepGeneration`), rule 5.
- A file of any other version, or not a world file at all, is one this build
  cannot read; rule 7 says it is never overwritten: it is MOVED to
  `.v<N>.unread` (a whole-number version) or `.unread` (anything else), under
  a numbered suffix (`.1`, `.2`...) if that name is taken, so a second never
  overwrites the first. `.bak` is left alone. (Decision B3-7: this happens at
  SAVE too, not only at load -- until B4 exists, a newer build's file could
  sit there when an older build saves.)
- Then `d2items.WriteFileAtomic`: a temporary file and a rename, retried while
  Windows holds the target.

The `.od2` now writes the same way (`HeroStateFactory.Save`: `.bak`, then tmp +
rename; BUG-48). The sidecar has NO `.bak`: it is rewritten on every equip,
level and fight's end, so its "previous generation" would be the last equip,
not the last save -- and the world file carries its own copy, so `world.bak`
is the previous save whole (decision B3-11).

## The verb: `Game.SaveWorld(SaveOptions)` (`d2game/d2gamescreen/save.go`)

1. **Arguments**: `omit` without `to` is refused (`errOmitNeedsTo`).
2. **Refusals** (a `*SaveRefusal`, `errors.Is` `ErrSaveRefused`; NO file is
   touched -- nothing has been read or written yet), in this order:
   - `NOT_READY`: no game; `NETWORK` (rule 9: the TCP handlers race the
     counted world stream); `NOT_READY`: no hero save opened, or no hero in
     the world yet;
   - `DEAD`: `died` or his body at 0 (checked BEFORE the fight: a man who died
     in a fight is `DEAD`);
   - `FIGHTING`: a fight running (`Combat.Fighting`), a paced fight holding the
     world (`WorldHeld`), the fight edge not yet taken back (`wasFighting`), a
     strike waiting on a walk (`pendingStrike`), a tactical pace or tile still
     out, or the journal still reading a fight (`journalFight`) -- and, after
     these, `Combat.Snapshot`'s own refusal (experience or paced minutes not
     yet taken, the pace window open) is `FIGHTING` too;
   - `TALKING`: `talk != nil` (a talk that reaches its end is ended by
     `Answer` at once, so this is "a talk is open"). A sleep's shelter is set
     only inside one answer's call and can never be seen by a caller, so it
     is not a refusal of its own (decision B3-10);
   - `JOURNAL`, `LOADOUT`;
   - `NOT_READY`: no kit (he has never chosen), or a world system missing.
3. **Snapshots**, every one a read: every B2 `Snapshot`, through ONE Resolver
   over the live map for spawns, notice and pursuit (`worldResolver`: an
   entity id is that entity wrapped as the live path wraps it -- `chaser` --
   and `player` is `prey{localPlayer}`; **B4b's load must build its Resolver
   the same way**), the sidecar bytes (`heroBytes`, the one document
   `saveKit` also writes now), the bodies, the entities, the scene, the map.
4. `World.Check`, `Encode(omit)`, and (without omit) `Decode` of the bytes.
5. With `to`: write ONLY the world file there, and stop (decision B3-3).
6. Otherwise: **the world file** (`WriteWorld`), then **his `.od2`**
   (`OnPlayerSave` -> the server's save, synchronous for a local client; its
   error now comes back, BUG-49), then **his sidecar** (the SAME bytes), then
   **the death screen's copy re-taken** (`snapshotHero`), so "load last save"
   after a death means this moment in all three files. A failure part-way
   says which files are written ("the world file is written and his .od2 is
   not"); the `.bak`s hold the save before.

**It changes nothing in the world.** No stream is drawn, no minute passes, no
system advances; the one thing a save moves is the death screen's copy.
`TestSaveResume` 7a and 7c: the state digest before and after is one digest;
control P1 (one draw from the world stream) is red on `[systems rng]`.

**It is not in `OnUnload`** and cannot be: `OnUnload` releases every world
system and nils the bodies before its `.od2` save. `OnUnload` is unchanged but
for one thing: a failed `.od2` save is logged and the unload goes on (the kit's
save, the client's close) instead of returning early (BUG-49).

unchanged at 37): refusal codes as error codes, `to`, `omit` (needs `to`;
`BAD_ARGUMENT` for a name that is not a block), and `world_path`, `written`,
`kept`, `set_aside`, `blocks`, `bytes` in its result. `d2app/harness_uuid.go`
hands the save the uuid reader's position (`SetUUIDStream`).

## Decisions (the recommended option taken each time; Josh can overturn any)

- **B3-1, `rng` holds copies.** The plan lists `rng {world, spawns, combat,
  rising, uuid?}` while B2 put each gameplay stream inside its own block.
  Taken: both, and `Check` refuses a file where a copy and its block
  disagree, so the copy can never be a second truth; `rng` is the one place a
  load reads to check every stream. (Alternative: `rng {world, uuid?}` only.)
- **B3-2, `scene.watch_clock` is saved**, against the plan's "D". Measured by
  reading `keepWatch`: a labour verb moves the clock inside a frame and the
  next frame credits the jump (capped at `watchJumpMinutes`); a save in
  between that derived the clock would credit nothing. With the menu or the
  dawn that gap cannot be hit; with a paused harness it can.
- **B3-3, `to` writes only the world file**, and `omit` needs `to`: a file
  with a block missing never replaces his save, and a negative control's file
  is a whole save of the moment (it embeds the sidecar).
- **B3-4, the sidecar is embedded whole** (its `version` too), the same bytes
  the sidecar file gets.
- **B3-5, positions twice where the load must be exact**: world tiles to read
  and compare (`x`, `y`), sub-tiles to restore (`pos`, `motion.pos`), held
  equal by `Check`.
- **B3-6, native = on the map when the screen is made.** B4b re-keys them by
  (`name_key`, `born`). A native that died and was taken off the map is simply
  absent from the list; B4b must remove what the map rebuilds and the file
  does not have. Natives carry their motion, but an NPC's patrol (path index,
  repetitions) is not carried (B2b: "only villagers patrol"), so a villager
  resumes his walk, not his patrol's count -- B4b's call.
- **B3-7, set aside at save as well as at load** (above).
- **B3-8, any change to a snapshot's JSON shape bumps `Version`.** Decode
  refuses unknown fields but NOT a missing nested field (it would read zero):
  a file from before a field existed would load that field as zero. There is
  no migration (plan section 6), so an added field is an incompatible change.
  **Nothing held this rule until the B3 review (B1): Decode now refuses a
  missing field at any depth, and the file's shape is pinned to its version
  by a hash and a golden file (`TestTheFileShapeIsPinnedToItsVersion`).**
- **B3-9, refusal order**: arguments, readiness and network, `DEAD`, then
  `FIGHTING`, `TALKING`, `JOURNAL`, `LOADOUT`.
- **B3-10, `TALKING` is `talk != nil`**; the shelter needs no refusal.
- **B3-11, no sidecar `.bak`** (above).
- **B3-12, a failed `.od2` save is an error to its sender** (BUG-49), and
  `OnUnload` logs it and goes on.
- **B3-13, the register**: `SaveWorld`, every B3 Snapshot row and the d2save
  verbs are HARNESS-ONLY until B5 gives the save its game callers; `Decode`
  and `World.Check` until B4a's load. What the game already calls is wire:
  `KeepGeneration` (every hero save), `HeroBytes` (every kit save),
  `Creature.SetCreatureID` (every creature the spawner places).
- **B3-14, a script's `strigoi_reseed_world` makes every later save refuse**
  (`INTERNAL`: the world stream is no longer on the game's seed, which no load
  could restore). Harness only; the game never reseeds mid-game.

## The decisions (R1-R9)

- **R1 (A1) -- a hero's identity is his name and class; a deleted hero's files
  all go.** The `.od2` holds no hero id or creation stamp, so the world file
  names `hero.name` and `hero.class` (the `.od2`'s `heroName`, `heroType` by
  name) and `World.CheckHeroFile` holds it to the `.od2` beside it. Name and
  class do not tell two heroes of one name apart; their NUMBER does, and the
  number is now never handed out while any file named after it remains
  (`firstFreeFileName`). Delete REMOVES (not sets aside) every file named after
  the save -- `N.od2`, `N.od2.bak`, `.tmp`, the sidecar, the world file, its
  `.bak`, every `.unread` -- because the player asked for the hero to be
  deleted; his `.od2` goes last and stays if anything else could not be
  removed, so he is still listed and the delete can be finished.
- **R2 (B3) -- natives by (`name_key`, `born`), held by the entity.** The
  review's recommended option. The pair is checked unique at save
  (`saveEntities` refuses) and in the file (`native-twice`). **B4b must re-key
  a villager IN PLACE** (the entity the map built, given its saved id) or
  capture the natives again after rebuilding them.
- **R3 (B7) -- the generation token is the world file's `saved_at`, carried in
  the sidecar as `generation`.** Built (about forty lines of code, under the
  review's sixty). The save writes it into both; every kit save between world
  saves writes the same generation (`Game.saveGeneration`, read back by
  `bindKit`), so the pair agree until the next world save and disagree only
  after a save cut off between its files. `World.SameMoment(sidecar file)`
  refuses the pair; **B4 falls back per rule 7 on that refusal**. The `.od2`
  carries no token -- it is upstream's format -- and needs none, by the
  invariant below.
- **R4 -- the `.od2` invariant, written down.** Of what the `.od2` carries,
  Strigoi's game changes only `Health` and `MaxHealth`. `Health` is the world
  file's (`hero.health`). `MaxHealth` is re-derived on every load from the
  sidecar's `BaseMaxHealth` and his talents (`applyProgress`); the `.od2`'s is
  read once, on a hero's first load, to seed `BaseMaxHealth`. Everything else
  it holds -- name, class, level, experience, attribute and skill points,
  mana, `MaxStamina` (his body's), gold, act, Diablo II's equipment and skills
  -- is written when he is made and never changed by Strigoi's game. So an
  `.od2` one save behind its world file resumes the same moment.
  `TestPlayerAndControlsFieldsClassified` labels each of those fields `O`
  (the `.od2`'s, never changed); a field Strigoi starts changing must move to
  the world file.
- **R5 -- stamina is saved** in the `hero` block (the review's recommendation:
  cheap and future-proof). The `.od2` never carried it (`json:"-"`).
- **R6 (B5) -- `to` is fenced in two places.** The harness makes it absolute
  and keeps it under `%APPDATA%` or the temporary folder and out of any source
  tree of this game (`harnessSaveTo`, reusing the editor's
  `harnessSourceTree`). `SaveWorld` refuses a `to` that is one of HIS files
  (in his folder, named after his save) **with or without `omit`** -- stricter
  than the review asked: without `omit`, a `to` over his world file would leave
  the world file one moment and his `.od2` and sidecar another. Both are
  `BAD_ARGUMENT` (`ErrBadSaveArgument`).
- **R7 (the order item) -- `WorldHeld` dropped, combat's own refusal moved.**
  `Combat.WorldHeld` is `encounter != nil && ...`, and `Fighting` is
  `encounter != nil`, the clause before it: it could never fire. The combat
  model's own refusal (`Combat.Snapshot`'s: experience or paced minutes not yet
  taken, the pace window open) now sits in `fightUnsettled` with the screen's,
  before `TALKING`, `JOURNAL` and `LOADOUT`. And one refusal is new: **his last
  swing still playing is `FIGHTING`** (`Player.isCasting`, found by classifying
  the Player's fields: the digest compares `casting` and the animation mode,
  and a load stands him still).
- **R8 (B2) -- strict at save runs the load's own checks.** `Validate` for the
  clock, light, rising and combat; for the five systems whose `Validate` also
  refuses a system in use -- squads, corpses, spawns, notice, pursuit -- a new
  `CheckSnapshot`: `Validate` is now that in-use refusal followed by
  `CheckSnapshot`, so the two cannot disagree; and the spawner's `Restore` got
  its check as `validate`. A refusal is an error, not a `SaveRefusal`: the live
  world holds something no load would take, reported `INTERNAL` with the
  block, before any file is touched.
- **R9 (B1) -- B3-8 has teeth in two halves.** `Decode` refuses a field this
  build writes that the file lacks, at any depth (`field-missing`); and the
  shape -- every path, JSON option and kind the `World` type writes -- is
  hashed and pinned to the version, beside a committed golden file of that
  version. Regenerating the golden file alone does not turn a shape change
  green: the version-1 hash is what it was.

# B4a (a quiet evening resumes) (branch `save-b4a`, 29 Sep 2026)

Josh's ruling is that the save "stops at that point then resumes at that
point". B3 wrote the file; B4a is the first code that reads one back into a
game, for every world that names no hostile entity. The acceptance test the
milestone was designed around -- save at T, step 120 world minutes, relaunch,
load, and the relaunched game equals the original at T and again at T+120 --
is green (`TestSaveResume` acts 1-6), and so is the death screen's "load last
save" in the same process (6b).

## The way in

Every way into a game goes through `App.ToCreateGame` (`d2app/app.go`), so
that is where a load begins: the character select's load, the death screen's
"load last save" (`App.ReloadGame`), the World Editor's playtest and the
harness's `strigoi_start_game`. A new hero has no world file (the hero screen
never hands out a number a file is named after: `firstFreeFileName`), so a
new game is exactly what it was. The menu's SAVE GAME is B5's.

## What loads, where, and in what order

The order is the authoritative one above ("The B4 load order"), and
`LoadReport.Steps` records it as it runs (the harness reads it:
`strigoi_start_game`'s and `strigoi_get_game_info`'s `load.steps`). Every step
is in `d2game/d2gamescreen/load.go` unless named.

| Step | Where | What |
|---|---|---|
| 1 | `PrepareLoad`, called by `App.ToCreateGame` before `d2client.Create` and `Open` | Read `N.od2.world.json`. Refuse (below) on rule 9, `d2save.Decode` (version, shape, `World.Check`), `CheckHeroFile`, `SameMoment`, and B4a's own limit (`huntedNight`). Then write the embedded sidecar over his sidecar file (re-indented: byte for byte the document the save wrote). The App then calls `d2server.SetNextGameSeed(file seed)`, `d2server.SetNextStartPosition(hero.pos)` and, in a harness build, reseeds the uuid stream from byte 0 of `rng.uuid`'s seed (`harnessLoadBegins`). |
| 2 | `CreateGame`, right after `NewClock` (`Game.restoreClock`) | `Clock.Validate`, then `Clock.Restore` (trap 1). Every system built after it samples the restored clock. |
| 3 | -- | B4b's: rebuild the entities. B4a rebuilds none. |
| 4 | the end of `CreateGame` (`Game.checkLoad`) | The game runs on the file's seed; the map is the file's (D5: generated either way, or the same SHA); the villagers the map built are the file's natives one for one by (`name_key`, `born`), each standing as saved (`checkNatives`); then every block's own `Validate` through one Resolver over the resumed map (`worldResolver`, the save's type): light, squads (a fresh owner), corpses (an empty registry), rising (against the FILE's corpses), spawns, the spawner's arrival, notice, pursuit, combat, the world stream (`StreamState.Check`) and the scene's stage. Nothing but the clock is restored. |
| 5 | the first frame, in `bindGameControls` after `bindKit` (`Game.resumeLoad`) | First the checks that need his kit and progress bound (`checkBound`): a kit (so the loadout choice is not holding the world), his saved health within the maximum `applyProgress` gave him, a carried torch only with a torch in his off-hand. Then, in order: his health; squads (s:1 in place); light WHOLE and the kit torch's `BurnLeft` zeroed (D1: step "torch"); corpses WITHOUT the open-count callback, `placeTheDead` skipped (trap 5); rising; spawns (their open bodies, counters, stream and the minutes to the next check from the file); the spawner's arrival; notice; pursuit; combat, and `paceRoundKey` derived from its last round; the scene, `lastStage` and `dawnPaidDay` together (trap 1, BUG-17), `watch_stood`, `field_dead`, `watch_clock`, `watch_clock_set`; then him -- standing at `hero.pos` bit-exact with no walk and facing `hero.facing` (`Player.StandAt`, rule 4), his stamina, his run toggle (`GameControls.RestoreRun`, the way the HUD's button flips it) -- and the region he stands in read at once (`checkRegion`: the sound environment is derived, and the saved game had long read it). |
| 6 | the end of `resumeLoad` | `MapEngine.RestoreRand(rng.world)` last, after everything that draws from the world stream (trap 6). In a harness build, the resume hook (`SetResumeHook`, `d2app/harness_load.go`) puts the uuid stream at `rng.uuid`'s count (`d2rand.RestoreReader`). |

| 8 | `Game.abandonLoad`, `App.FallBackToDawn` | A refusal anywhere tears the whole game down and falls back per rule 7 (below). |

**A half-restored world never runs a frame.** A loading game binds its
controls at the TOP of its first `Advance` (a fresh game binds at the end of
its first frame, as before), restores there, and returns before anything else
of the frame when a load is still pending or was abandoned. In a harness game
under the stepped clock every frame before `start_game` returns has a zero
delta anyway; in the shipped game the first frames have real deltas, and none
of them reaches `advanceWorld` before the file is back in it. The save refuses
`NOT_READY` while a load is pending or abandoned.

**D1, as built (decision B4a-1).** The brief said to write the embedded
sidecar with the torch's minutes zeroed. B4a writes the sidecar byte for byte
as the save wrote it -- the torch's minutes in it -- and zeroes them in the
kit the load BINDS, which is D1's own wording ("the kit the load binds"). Two
reasons: a file refused after the sidecar is written (a changed map, a block
the load refuses) falls back to dawn from that sidecar, and a zeroed torch
there is a torch that will not light (`BurnLeft <= 0` is "no torch" to L); and
the death screen's copy (`snapshotHero`, taken by `bindKit` from this file) is
then the save's document exactly. The unit test and the ui's new
`kit_torch_left` hold the zeroing; control P18 shows it red.

## The refusals

Each is a `*LoadRefusal` (`errors.Is` `ErrLoadRefused`) with a code, written
to the log (`LOAD refused ...`) and to the harness's load report (`refused`,
`reason`, `set_aside`, `fell_back`). The player-facing notice is B5's.

| Code | Where | When | The file |
|---|---|---|---|
| `NETWORK` | step 1 | a LAN host or client (rule 9) | ~~stays (decision B4a-2)~~ **set aside since the review fixes** (B4a-R1: staying, it lost the network evening to the next load, BUG-61). He begins with his hero, kit and progress. |
| `VERSION` | step 1 | a version other than 1 | set aside `.v<N>.unread` (or `.unread`) |
| `FILE` | step 1 | version 1 and not a file a load could read (`Decode`); or not readable at all | set aside `.v1.unread` (one not readable at all: `.unread`, since the review fixes -- before, it stayed) |
| `HERO` | step 1 | another hero's file (`CheckHeroFile`: name and class) | set aside |
| `TORN` | step 1 | his sidecar missing, or of another generation (`SameMoment`) | set aside |
| `HUNTED` | step 1 | B4a's limit: a pack on the map, a watch, a chase, a monster's body, an entity the map does not build, a squad with a deployed model (D3) -- B4b's | ~~set aside~~ **stays for B4b since the review fixes** (B4a-R3); his sidecar untouched |
| `SIDECAR` | step 1 | his sidecar file could not be kept (`.preload`) or written | ~~stays~~ **set aside since the review fixes** (B4a-R1), his own sidecar put back |
| `SEED` | step 4 | the game did not run on the file's seed | set aside; torn down |
| `MAP` | step 4 | another map (D5) | set aside; torn down |

| `BLOCK` | steps 2, 4, 5 | a system's own check refused its block (or `checkBound`'s) | set aside; torn down |

**Falling back.** A refusal at step 1 needs nothing torn down: nothing was
opened, and the game begins at dawn from his sidecar. A refusal at step 2 or 4
returns from `CreateGame`; `startGame` closes the client (BUG-25's path), and
`App.ToCreateGame` sets the file aside and calls `App.FallBackToDawn`. A
refusal at step 5 cannot come from the file's blocks (they were validated at
step 4) but from `checkBound` or a Restore that disagreed with its Validate;
`abandonLoad` marks the game abandoned -- its `Advance` returns at once, its
`OnUnload` writes neither the `.od2` nor the sidecar -- sets the file aside and
calls the same fall-back. `FallBackToDawn` re-arms the refused game's seed
(`SetNextGameSeed`; in a harness build the uuid stream too) and goes through
`ReloadGame`, so the old game's server lets go of its port first: the dawn
that replaces a refused load is the dawn a fresh launch of that seed would be.
The report of a refusal after the game opened is kept by the dawn game
(`fell_back`: it finds no file, having set it aside). **The review fixes
changed this paragraph's world** ("B4a review fixes" below): every refusal
of a prepared load puts his own sidecar back first (A1), the dawn runs on the
file's seed (C3), a file that cannot be set aside is not read again in the run
(B1), and the dawn keeps the report for itself only.

**Decision B4a-3: "hold anything" is read as "hold a group, a watch or a
chase".** The spawn tables always hold something -- open bodies, their
counters, their stream, the minutes to the next table check -- and so do the
notice and pursuit totals. B4a restores all of them when they name no entity
(the brief's "everything that names no hostile entity"); without the spawns
block act 4 is red on `spawns` (measured: control P8), and trap 5's "open
bodies from the file" is exactly the spawns block. So `Spawns/Notice/Pursuit
.Restore` and `gameSpawner.Restore` are called by B4a, through the save's
Resolver type, with nothing for it to resolve.

**Decision B4a-4: B4a rebuilds no entity**, so any entity that is not a native
is a refusal, and so is any monster body (bodies live with entities) and any
squad beyond s:1.

**Decision B4a-5: the natives are checked, not re-keyed.** By (`name_key`,
`born`) one for one, and each native's saved motion must be the motion of the
villager the map just built (JSON-equal): the authored village's villagers
stand, so in every quiet evening measured they were; one who walked would
need `NPC.RestoreMotion`, which is B4b's. In a harness game the villagers'
ids are also the file's (the uuid stream from byte 0 of its seed); in the
shipped game (crypto/rand ids) they are new each launch, and nothing B4a
restores names a villager by id -- the re-key is B4b's.

## The harness: both paths, and the dials

- **The uuid stream on both paths** (B1 notes section 1). A load reseeds the
  harness's uuid reader from byte 0 of the file's `rng.uuid` seed before the
  game opens, on a fresh launch and on "load last save" alike, so the
  connection and the villagers draw the ids the saved game drew; the resume
  hook then puts the reader at the file's byte count. Before B4a "load last
  save" continued the dead game's stream. (The seed itself is the file's on
  both paths: `SetNextGameSeed` in `ToCreateGame`.)
- **The dials** (step 7). `strigoi_set_system_field` records every write to a
  field `harnessDialFields` lists as a dial (clock frozen/moon; combat's
  twenty-one tuning fields; pursuit arrive_within/repath_tiles; rising
  edge_floor/hasty_weight/p/pressure; spawns chance/check_minutes/max_groups/
  notice_lit_level/notice_radius/rout_at); a load re-applies the last value of
  each, in first-written order. State (meters, light sources, open bodies, a
  group's morale) and verbs (commit, despawn, release, round) are never
  written again over what the load restored. A fresh process has recorded
  nothing: its script sets its dials after `start_game`, as act 4 does.
- **`start_game`** loads the world file when one is there (it goes through
  `ToCreateGame`), reports what the load did (`load`), and refuses
  `BAD_ARGUMENT`, starting nothing, when `seed` is not the seed the file was
  saved on (decision B4a-9; the plan had this in B4b's row). A load with no
  `seed` resumes the file's.

## The re-key verb (`MapEngine.RekeyEntity`, `MapEntityFactory.Rekey`)

B2b noted that the verb the load order's "villager re-ids" needed did not
exist. It does now, in two halves on the seam's model:

- `MapEntityFactory.Rekey(e, id)` (`d2mapentity/entity_id.go`) sets the id on
  an NPC or a creature IN PLACE and counts it as given, so the seam never hands
  it out. Refused with `ErrEntityID`, changing nothing: `""` or `player`; the id
  waiting in the seam; an id already handed out (to another entity); any other
  kind. Re-keying an entity to the id it already has is allowed.
- `MapEngine.RekeyEntity(e, id)` (`d2mapengine/entity_id.go`) adds the map's
  checks -- the entity must be on this map under the id it answers to, and no
  other entity may hold the new id -- and moves the engine's own key. The
  entity stays the same pointer, so everything that holds it (the screen's
  natives, a talk, the headman's post) still does.
- **Why it matters, and where it is proved.** In a harness build the map
  draws the villagers' ids from the uuid stream reseeded from the file's seed
  (B4a), so they ARE the file's and the re-key is the identity: acts 4-6g could
  never see it. The shipped game's ids come from crypto/rand, new every
  launch. So act 6h gives T's file its villagers' ids as another launch would
  have made them (each native's id, everywhere in the file, made another; a
  suffix keeps the entity list's order) and loads it: each villager answers to
  the file's id, the map's own is gone, and the resumed game saves that file
  byte for byte but its stamp. Control H5 (the re-key taken out) is green at
  acts 4-6g and red at 6h -- the identity case cannot see it, which is why 6h
  exists.

### B1 -- a death still playing at the save played again after the load (BUG-75, BUG-76)

**What the review found.** A monster slain while it walked in -- the quick
resolve's last quarter, still on its chase -- walked on through its whole
death: `Creature.Advance` (and `NPC.Advance`) kept calling `Step` while the
death was held, and only the end of the death stopped the walk. Its corpse
came to rest up to about a tile further along its route than where
`Combat.fallCorpse` recorded the fall. And a save made while a death played
resumed it from its first frame (`RestoreMotion` restarts a held action),
so the resumed death ended later than the saved one: the review's real-game
probe had two opportunists `dead` sixty frames after T' in the saved game and
still `death` in the resumed one. B2b's Motion note ("then lies as a corpse,
as it would have") was untrue; it is corrected in place.

**The fix, in two parts, both as recommended.**

1. **BUG-75: a death ends the walk where it begins.** `mapEntity.halt`
   (`map_entity.go`) clears the route, puts the target where the entity
   stands, zeroes its velocity and drops the arrival -- WITHOUT turning it
   (`StopMoving` would: it points the directioner at the entity's own
   position). `Creature.StartAction` and `NPC.StartAction` call it when the
   action is a death, and both `Advance`s no longer step a body playing its
   death (`dying()`), so even a route handed to it then is not walked. The
   corpse lies where the resolver recorded the fall, and turns when the death
   ends, as it always has. No die, dial or roll was changed for it, and no
   existing assertion (the unit and playtest suites below are green without
   one being edited for it). What does change in play is where a corpse lies
   -- and so, for a packmate's tactical walk, which tile it occupies -- now
   where the fall was recorded rather than up to a tile on.
2. **BUG-76: no held action is saved or loaded.** Of the two options the brief
   allowed, **the refusal was chosen: it is exact and simpler.** Restoring a
   held action at its saved frame would carry the frame AND the time into it
   (`Animation` has no accessor for the latter, and an NPC's composite keeps
   its own per mode) -- a new world-file field and new engine accessors, for a
   moment that lasts a second. So `Game.heldAction` (`save.go`) refuses the
   save, `FIGHTING`, while any monster or villager holds an action -- a swing,
   a blow taken, a death -- naming it ("... is still playing its death: a save
   carries no animation's frame"), as his own swing is refused; and
   `heldInFile` (`load.go`) refuses a file that holds one anyway -- `ENTITY`
   for a monster, `NATIVES` for a villager -- before anything is rebuilt: no
   save of this build writes one, and resumed it would restart.
   `RestoreMotion` still restores a held action (its unit tests stand); the
   game no longer asks it to.

**What it shows:**

- **Not one refusal was of another kind.** Every refusal was a held action
  (`A1`, `GH`, `DT`), so Q5 (a) holds as written.
- **The holds outlast the round.** A round's swing (`A1`) and flinch (`GH`)
  hold an entity **38 frames** (0.63 s). A death (`DT`) holds **56** (0.93
  s).
- **So at the shipped round the holds overlap.** A round comes every 24 frames
  at night and every 15 at dawn, one world minute at 2.5 and 4 minutes a
  second.
- **The only frames that took a save were the ones before each fight's first
  blow.** The refused run is the whole fight, plus its last death.
- **The run grows with the fight, and the measured fights were short.** These
  61-hit-point quarries died in about 6 rounds. A raid night's village fights,
  one after another, would refuse the save for as long as they run. **So
  "retry until accepted" waits for the village to stop fighting.**
- With a round of 4 minutes, a save waits at most 56 frames.

**The options, for Josh (recommended first):**

- **(a) Carry the held action's frame in the world file, and drop the refusal
  for held actions (a B5 prerequisite).** `d2mapentity.Motion` gains the
  action's elapsed frame, and `RestoreMotion` resumes it there. The file's
  shape changes: version 3, a new golden, and the B3-8 check. This is the exact
  fix. BUG-76 refused only because the file carried the mode and not its
  frame. It removes the wait from B5's autosave and menu save whenever anyone
  fights, in the village or in a pack.
- **(b) Narrow the refusal to deaths (`DT`), and resume a swing or a flinch
  from its first frame.** Smaller, but no longer exact: the resumed swing ends
  up to 38 frames later than the saved one, and the digest compares `held` and
  `animation_mode` (BUG-82). The world could differ for about a second, and for
  longer if a held action gates a walk.
- **(c) Keep the refusal, and let B5's saves wait.** The autosave retries
  until the village's fights are over; the menu save says "not while they
  fight". This is simplest, but on a raid night the save may be unavailable
  for minutes.
- **(d) Retune the round.** At `round_minutes` 3 or more a save waits at most
  a second. This changes the pace of combat, not the save rule, so it is a
  combat ruling and not a save fix.

**Not decided here.** The merge scripts slow the round (option (d)'s effect,
in the tests only), so that they test resume exactness and not this refusal.

# B5: the save reaches the player (branch `save-b5`, 29 Sep 2026)

Josh's ruling is that the save "stops at that point then resumes at that

## The menu (rules 1 and 2)

- `d2player.MenuSaver` is the menu's one view of the save: `SaveRefusedNow()`
  (why not, in words, or "") and `SaveFromMenu(exit)` (saved, or not and why).
  The menu never sees a code, so a refusal the save gains or loses changes
  nothing in it. `CreateGame` hands the game screen to the menu
  (`EscapeMenu.SetSaver`).
- `EscapeMenu.open` asks `SaveRefusedNow` BEFORE the layout is set, so the
  entries are placed around the line they show; `showSave` sets the exit
  entry's words and the note's lines (three labels, each centred: a d2gui
  label of two lines draws them left-aligned).
- `Game.SaveRefusedNow` is the save's own refusal (`saveRefusal`), asked and
  not acted on: a read.
- **"Save and Quit"** is the plan's SAVE AND EXIT GAME (rule 1: "The menu has
  SAVE GAME (keep playing) and SAVE AND EXIT GAME"). It was there, and saved
  only his hero (BUG-96); it saves the moment now. SAVE GAME is new.

## The close hook (rule 3)

- `ebiten.SetWindowClosingHandled(true)` when the App has a hook
  (`Renderer.SetCloseHandler`, from `App.Run`). `Renderer.Update` asks
  `ebiten.IsWindowBeingClosed()` before the frame advances; if so it calls the
  hook and returns `ebiten.Termination` (a clean exit of `RunGame`). No frame
  of the game advances once the window is closing. Before B5 the close ended
  the process with no `OnUnload` at all (BUG-95).
- `App.closeTheGame` (`d2app/close.go`) runs once: the game in play, if any,
  goes through `Game.CloseGame(10 s)`, and `App.closed` then stops every
  frame and every draw (the screen it unloaded is still the screen manager's
  current one).
- `Game.CloseGame` runs the hook on a goroutine of its own while the caller
  waits for nothing else: `SaveWorldAs(close)` -- SaveWorld, the world file,
  his `.od2`, his sidecar, in B3's order, the generation in both -- and then
  the screen's own `OnUnload`, which writes his `.od2` and sidecar as it always
  has (of the SAME generation: SaveWorld set it) and closes the client. A
  refused save (a fight) still unloads: his `.od2` and sidecar are written of
  the LAST save's generation, so the world file still pairs with them and the
  next load resumes the last save, its embedded sidecar over the newer one --
  rule 3's "you come back to your last save", measured (`TestTheCloseHook`
  act 3). A panic inside the hook is a report, not a crash of the close.
- **It never hangs the close.** Past the limit the caller stops waiting and
  the process leaves. B3's order is what makes that safe: a save cut off
  between its files is a sidecar of another generation, refused TORN at the
  next load and set aside (rule 7), never half-resumed.
- **The harness's `strigoi_quit{graceful: true}`** runs the same
  `App.closeTheGame` on the game goroutine, then exits: the playtests' way to
  the close (a script cannot press a window's X). What they do not reach is
  the two ebiten lines; those are read, not tested.

## The dawn autosave (rule 10)

**Armed** in `earnExperience`, on the frame `nightSurvived` pays the night and
`dawnWatch` settles the promised watch (the plan's section 7: "after
`dawnWatch` has settled the night (the same frame `nightSurvived` pays)").
Not in a network game (rule 9: never saved), and not under the harness's
dial. **Tried at the END of that frame** (`advanceAutosave`, `Advance`'s last
line): after the night's experience, the watch, the journal's dawn lines, the
map's animations and the controls -- the state a harness save sees between
frames, so "the moment it was taken" is a moment a relaunch can be held to.

| State | Means | Leaves by |
|---|---|---|
| `idle` | no dawn has armed one in this game | a dawn: `pending` |
| `pending` | armed; tried at the end of every frame | a frame that saves: `taken` (by `dawn`); his own save while it waits: `taken` (by `menu`, `harness`...) -- `cover`; night falls first: `dropped`; a save that is not a refusal fails: `failed` |
| `taken` | the day's save is made | the next dawn: `pending` |
| `dropped` | night fell with every frame refused; a log line (Warning) and a quiet notice | the next dawn |
| `failed` | the write failed; logged (Error) and a notice; **never retried** -- a disk that refused a write would otherwise be written every frame | the next dawn |
| `off` | the harness's dial `save.autosave` false | the dial on, and the next dawn |

- **Any refusal is "not now".** The machine never reads the code: FIGHTING,
  TALKING, a monster's held action (B4b's refusal, BUG-87's shape) and a code
  this build has never heard of all leave it pending (the unit test runs
  four codes, one of them invented). So when `save-held` drops the held-action
  refusal, nothing here changes: the autosave is simply taken sooner.
- **It outlasts BUG-87.** Measured on master: a clock fight refuses 92-93% of
  its frames in runs of up to 392 (6.53 s). The unit test holds it pending
  through 1000 refused frames in each of dawn, day and dusk, tried on every
  one and on none after it took; the playtest's fight across first light was
  refused 560 frames and the autosave was taken 60 frames after the fight
  ended (the dog's death still playing).
- **The window is "that day": until night falls** (`autosaveWindowOpen`:
  dawn, day, dusk; NightStart, 21:15, ends it). The plan's section 7: "it
  saves at the first moment that day when saving is allowed. It does not skip
  the day." (Decision B5-2 below, and a question for Josh.)
- **At most one per dawn.** `arm` replaces the last dawn's state; the file
  carries `dawn_paid_day` and `last_stage`, so a game resumed at dawn arms
  nothing (measured, `TestTheDawnAutosave` act 2).
- **A save of his covers it.** A menu save, a close or a harness save made
  while it waits is the day's save: the autosave is `taken` by it, instead of
  writing the same moment again a frame later.
- **Log lines** (`strigoi.log`): `AUTOSAVE armed: the dawn of day N`;
  `... pending (N refused frames; CODE: reason)` on the first refusal and
  every 60th; `... saved` / `... saved after N refused frames (the last
  CODE: reason)`; `... dropped -- night fell after N refused frames ...; the
  last save stands` (Warning); `... the save failed: ...` (Error); and
  `... is taken by the menu save`.
- It is not in the world file: at every save it is not pending (the save
  covers it), and a resumed game's own state is derived (`idle`, and the
  file's `dawn_paid_day`). `TestGameFieldsClassified` labels the four new
  `Game` fields D.

## Rule 3, as built now

> **Closing the window does what SAVE AND EXIT does. Only his live fight,
> his death or a network game makes it leave without saving -- and then he
> comes back to his last save.**

- The close first **ends what only holds the screen**: a talk
  (`Game.EndTalk`) and his journal (`journalOpen = false`), exactly as a
  death ends them (`noticeDeath`). Neither is anything the world file keeps.
- It then **lets the moment after a fight settle**: while the save is
  refused `FIGHTING` with no fight of his (the fight's end not yet applied,
  his last swing, a blow or a death still playing), it runs frames -- up to
  eight seconds of game time and never more than four seconds of the
  close's wall time -- and saves as soon as the refusal clears.
- **What is left that leaves unsaved**: his live fight (`FIGHTING` with his
  fight running), his death (`DEAD`), a network game (`NETWORK`). A game
  still starting (`NOT_READY`) or his gear not yet chosen (`LOADOUT`) is
  refused too and loses nothing: the world has been held, or not yet built,
  since the game opened. The kit panel and the help screen are not refusals
  at all (they hold neither the world nor the save), so a close with either
  open simply saves.
- **Until save-held merges**, one more: a village's fight whose held actions
  (BUG-87: 6.53 s at most measured at the shipped round) outlast the
  settle's eight seconds. save-held drops that refusal; after the merge the
  settle only waits out his own swing and the fight's end, a frame or two.

## The TORN recovery, as built now

> **A save cut off between its files resumes the save before it.**

A save writes the world file, then his `.od2`, then his sidecar. A save that
stops after the world file landed -- a crash, a power cut, a close past its
limit, a write that failed and could not be put back -- leaves the new world
file beside the last save's sidecar, and the last save itself as the world
file's `.bak` (WriteWorld keeps it before writing). The load refuses the world
file `TORN` (its moment is not his sidecar's). **When the `.bak` is his
sidecar's moment** -- this hero's, and `SameMoment` with his sidecar, every
check step 1 runs on a world file -- the torn file is set aside as
`N.od2.world.json.torn.unread` (kept, never deleted), the `.bak` is put in
its place, and the load goes on with it. He is told: "Your save was cut off
while it was being written." / "The save before it is restored. The cut-off
save is kept, set aside -- not deleted." (`LoadReport.FromBak`; the load's
`notes` say what was done). A `.bak` that is not his sidecar's moment is not
resumed, and the load is refused `TORN` as before (rule 7: set aside, dawn).
`PeekLoad` (the seed a start is held to) sees the `.bak` too.

### B1 -- the close's limit could cut a save inside a file (BUG-99)

- **Fix, the recommended option** (`d2items.WriteFileAtomic`,
  `RenameRetrying`, `CutWrites`; `waitForClose`, `closeGrace`):

    The fallback existed for a reason -- Windows refuses a rename while
    anything holds the target (the 23 Sep measurement: a polling reader, in
    the field a scanner, the indexer, Explorer's preview) -- so the RETRY
    stays and grows (twenty 25 ms waits, then 100, 200, 400, 800 ms: two

    refused is the write's failure; the world save puts its world file back
    (A2), and a kit save is made again by the next one.

    (`ErrWritesCut`) and the one in flight is waited for, up to `closeGrace`
    (3 s, longer than one write's retries). A disk that hangs past that is
    reported (`close.cut_mid_write`) -- and since nothing is written in place,
    the file it would have replaced is whole. A cut between files is the
    TORN recovery's case.

## The decisions (the recommended option each time; Josh can overturn any)

- **B5R-1, the settle's bound:** eight seconds of game time (the longest
  BUG-87 refusal measured at the shipped round is 6.53 s) and four of wall
  time, well inside the close's ten. The review's recommendation, with the
  bound chosen to outlast the measured worst case until save-held merges.
- **B5R-2, LOADOUT and NOT_READY stay refusals of the close**: nothing he
  played can be lost (the world is held or not yet built), and a close cannot
  choose his gear for him.
- **B5R-3, never write in place, anywhere** (B1's recommended option), not
  only while closing: a torn file is worse than a failed save now that a
  failed world save puts itself back.
- **B5R-4, B2's guard is SaveWorld's step 0**, not WriteWorld's: d2save does
  not know what the load refused.
- **B5R-5, after a put-back the `.bak` is the last save** (WriteWorld's
  copy), not the save before it: the spec's "restore from the `.bak`
  WriteWorld just kept", and the files agree.
- **B5R-6, the controls are overlays**: the mutation is real source, built,
  and the worktree is never changed while other runs read it.
- **B5R-7, the attached-mode guard is the playtests'**: a game started by
  hand with the harness keeps every verb (a person driving it is choosing
  to); a script is refused before it writes the real user's saves.
- **B5-2 kept: a pending autosave waits until night falls** (C6). The
  trade-off, for Josh: a dawn refused for hours -- a fight at first light,
  then a noon fight that goes badly -- is taken at the first savable moment
  that day, which may be after the bad fight, replacing his last good save
  (the dawn's, or an earlier one) with a worse moment. The alternative (the
  window ends at sunrise, 22 seconds after first light) drops the day's save
  whenever first light's fights outlast it, and a crash that evening costs a
  night and a day. **Question for Josh**, below.
