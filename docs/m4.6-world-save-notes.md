# M4.6 world save: carry-overs from B1's review

Short, and owned. Each entry below is something burst B1 (the counted streams
and the observed fields, branch `save-b1`) found and did NOT build, with the
later burst that owns it. Written 27 Sep 2026 after an independent review of
B1; the build plan itself is the main session's.

## 1. "Load last save" is not a seeded game (owner: B4b)

Only `strigoi_start_game` seeds a game. It sets the server's one-shot seed
(`d2server.SetNextGameSeed`) and reseeds the harness's uuid stream
(`d2app/harness_uuid.go`), then begins the game. The death screen's "load last
save" goes `App.ReloadGame` -> main menu -> `ToCreateGame` (`d2app/reload.go`)
and does neither, so the reloaded game, in a process that was seeded:

- takes a **wall-clock server seed**: `takeNextGameSeed` is one-shot and the
  first game consumed the override. The world RNG, the spawn tables, combat and
  the rising all seed from `gameClient.Seed`, so all four start where no script
  chose;
- **continues the uuid stream** from the dead game's byte count: its player id
  (the connection's uuid) and every entity id are the seed's later ids;
- therefore matches **no fresh launch**. It is deterministic only for the same
  script in the same process.

How to see it: the `uuid` provider reports `seeded_for_this_game` (false on a
reloaded game), `games` (= `seeded_game + 1` there) and `bytes_at_game_start`
(the dead game's count); every stream's `rng.seed_str` shows the wall-clock
seed. Pinned as it is today by `d2app` `TestUUIDStreamOnAFreshLaunchAndOnAReload`
(both halves) and `TestTownWalkDeterministic` (the fresh half).

**B4b** restores these on a load: the server seed from the save, and the uuid
stream with `d2rand.RestoreReader(seed, bytes)` AFTER the entities are rebuilt
(the plan's trap 6). When it does, the reload half of the unit test changes
with it, on purpose.

## 2. Seeds are int64; decode them as int64 (owner: B2, the world file)

A wall-clock seed (UnixNano, ~1.8e18) is past 2^53, where float64 stops
holding every integer. A reader that decodes JSON into float64 -- every
playtest's `mustNum` does -- reads a DIFFERENT seed, and a stream restored from
it is a different stream from its first value. So every stream report carries
`seed_str` (exact decimal) beside `seed`, and **the world file must decode
seeds as int64** (`json.Decoder.UseNumber` then `Int64`, or a typed struct
field), never through `interface{}`/float64. `d2rand`
`TestSeedStrSurvivesAFloat64Decoder` shows the loss and both exact routes.

## 3. A stream is one value (done in B1; for B2's Restore)

Spawns, Combat and Rising each hold one `*d2rand.Stream` (the `*rand.Rand` and
its counted source), and `Stream.Restore(seed, draws)` replaces both at once.
B2's system Restore calls that and nothing else. Do not take `.Rand` out of a
stream and keep it: after a Restore it draws from the old, uncounted source.
The map engine is the exception, because its stream is handed to two factories:
`MapEngine.RestoreRand` goes through `useRand`, which re-hands it, and
`TestRestoreRandHandsTheStreamToTheFactories` holds it there.

## 4. A pack's members include its dead (for B2's snapshot)

`group.members` is never shortened: a death unwatches its member (combat's
`withdraw`) and the group keeps him, and the game reads the dead there --
`spent()` is "no member still watched" over the whole list, a dead man's
profile still names his pack, and a despawn takes every member off the map. `spawns.group_list[].member_ids` reports every
member as placed, dead ones included; the `notice` rows are only the watched.
The snapshot must carry `member_ids`, not the notice rows.

## B2b: the snapshots that carry entity ids (27 Sep 2026, branch `save-b2b`)

B2b built the three world snapshots that point at entities (Spawns, Notice and
Pursuit), the `Resolver` that turns saved ids back into live things, the
next-id seam, the motion snapshot and the game spawner's arrival count.
Nothing calls any of it yet. B3 writes the snapshots into the world file and
B4b restores them. Every new verb is in the reachability register as
`defer`/`dead` (`tools/reachcheck/register_b2b.go`), so the gate goes red the
day B3 or B4b calls one and forces the row to `wire`.

### Identity

- **`d2world.Resolver`** (`resolver.go`): `Watcher(id)` returns the live
  watcher with that entity id, and `Quarry(ref)` returns the player for
  `PlayerRef` ("player") and an entity otherwise. A chase's hunter resolves
  through `Watcher` and must also be a `Hunter`, the same type assertion
  `startChasesForTheAware` makes.
- **Strict both ways.** Every restore checks that what the Resolver returns
  answers to the id it was asked for. A saved id that does not resolve is
  `ErrUnresolvedRef`, never a silent drop.
- **The same Resolver at save.** Each `Snapshot(r)` takes a Resolver over the
  live world:
  - it names the player, whose live id is written as the word "player";
  - every saved ref must resolve at save, so a file no load could read is
    refused before it is written;
  - Spawns uses it to mark which members are `gone` (below).
- **Restores are all-or-nothing.** A refused snapshot leaves the system exactly
  as it was.

### The next-id seam and the motion snapshot (d2mapentity, d2mapengine)

- `MapEntityFactory.SetNextEntityID(id)`: the next `NewNPC` or `NewCreature`
  takes the id, once, and ids then come from the uuid stream again.
- **A duplicate is refused with `ErrEntityID`, not a panic.** Refused: an id
  already given out through the seam; an id set while another is still
  waiting; `""` and `"player"`. `MapEngine.SetNextEntityID` shadows it and also
  refuses an id already on the map (`AddEntity` would silently overwrite).
  **B4b calls the engine's.**
- The id is taken by every construction attempt, including a failed one, so a
  failed rebuild cannot hand its id to the next entity.
- A set id draws nothing from the uuid stream. The load restores the stream's
  count after the entities (trap 6).
- `PendingEntityID()` lets the load assert nothing is left waiting.
- `Creature`/`NPC` `.MotionSnapshot()` / `.RestoreMotion(Motion)`:
  - **carried:** position, target, velocity, waypoints (all in raw sub-tiles,
    so bit-exact), speed, facing, animation mode, a held action and the corpse
    pose;
  - **not carried:** the arrival callback (every monster's walk is handed over
    with none), the animation frame (a held action restarts from its first
    frame), and an NPC's patrol (only villagers patrol, and they are D);
  - velocity is recomputed by the first step, so it is seen only at the load
    (the renderer's debug overlay); the test pins that;
  - RestoreMotion sets fields directly, never through `setTarget`, which would
    re-derive an NPC's mode.
- **Rule 4 is the player's alone.** There is no MotionSnapshot on `*Player`.
  Monsters, the risen and deployed squads keep their motion.

### Each snapshot's fields

**Spawns** (`SpawnsSnapshot`):
- **S:**
  - groups: id, row, code, members, morale, born_at, band, stage (by name),
    weight, spawned, born_where;
  - `next_id`, `since_check_minutes`, `open_bodies`;
  - the eight counters;
  - `rng_seed` (a JSON string, exact past 2^53) and `rng_draws`.
- **T:** `sheltered`. Snapshot is refused while it is set.
- **D:** the dials, and the wiring.
- **Members** are `{id, x, y, gone}`, dead ones included.
  - A member on the map must resolve at load, to an entity standing exactly at
    the saved x,y. The position is an identity check: the wrong entity, or one
    whose motion was not restored first, is refused.
  - A **gone** member is one who was in his group and not on the map at save: a
    slain man whose body stood up, so `takeOffTheMap` took his remains.
    - He must NOT resolve at load; if he does, the load is refused.
    - He comes back as a stand-in (`b2bGoneMember`) answering to his id and
      last place.
    - His x,y is carried and nothing reads it. The sweep pins that, so it goes
      red the day something does.
- Group ids are checked below `next_id`, rows against this build's tables, and
  bands in -1..2.

**Notice** (`NoticeSnapshot`):
- **S:** per watch: watcher id, target ref, sees, noticed, distance,
  light_at_target, reach, since_check, since_seen, checks, notices. Also the
  two totals.
- **T:** `hidden`. Snapshot is refused while it is set.
- **D:** every dial. **The radius is never saved** (trap 7), and a test pins
  that a restore keeps the radius the model was built with. `reach` is saved:
  it is the last sight test's result, not the dial.
- Restore evaluates nothing (`Watch()` would run a sight test).

**Pursuit** (`PursuitSnapshot`):
- **S:** per chase: hunter id, quarry ref, solved_at_x/y, solved_distance,
  since_solve, reachable, solves, arrived. Also the total solves.
- **D:** the dials, and the router.
- Restore solves nothing and hands no hunter a path. The route is the hunter's
  own motion.

**gameSpawner** (`SpawnerSnapshot{arrival}`, `game.go`): refuses a negative
count. Lost, the next pack comes from the first pack's bearing.

### For B4b: the load order this relies on

1. Rebuild each saved entity: `engine.SetNextEntityID(id)`, then
   `NewNPC`/`NewCreature`, then `RestoreMotion`. **Motion before Spawns.Restore**,
   because a member must stand where he was saved.
2. Then `Spawns.Restore`, `Notice.Restore` and `Pursuit.Restore`, all with one
   Resolver over the resumed map, and `gameSpawner.Restore`.
3. Then the uuid count (trap 6), and check `PendingEntityID()` is empty.

### Found, and left for later bursts

- **Villager re-id (B4b).** The seam covers entities the load builds.
  Villagers already exist when it runs, so re-iding one needs a verb that
  changes an entity's id and re-keys the engine's map. That verb does not
  exist.
- **Harness-set dials are not saved** (dials are D). A script that raised
  `chance` or `max_groups` before saving resumes on the defaults. TestSaveResume
  (B4) must re-apply its dials after the load.
- **NPC poses with a composite** are not unit-tested: a composite needs the
  MPQs. The NPC's walk is tested without a composite; the creature path (PNG)
  is tested in full. B4b's playtest covers the NPC composite.
- **A held action restarts from its first frame.** Saves are refused during a
  fight, so only a swing's tail after a fight can be cut short.
